# 技術調査 (ライブラリドキュメント)

ライブラリ・フレームワーク・SDK・API・CLI ツール・クラウドサービスの仕様や使い方を調べる場面で、学習データに頼らず現行ドキュメントで裏取りするためのルール。取得手段は WebSearch・WebFetch とし、本ルールは「いつ引くか」「どの情報源を一次情報とするか」「どのバージョンを引くか」「取得結果が部分的だった場合の回答の扱い」「repo 固有の調査手段がある場合の優先順位」「subagent へ委譲するときの扱い」を定める。

## 原則

- MUST: ライブラリ・フレームワーク・SDK・API・CLI ツール・クラウドサービスの API 構文・設定方法・バージョン移行・セットアップ手順・CLI の使用方法を調べるときは、WebSearch・WebFetch で現行ドキュメントを取得する。ユーザの質問に回答する場面と、実装計画を立てるための調査の場面の両方に適用する。
- MUST: 対象リポジトリの CLAUDE.md 等でそのライブラリ向けのドキュメント調査手段 (repo 同梱の skill 等) が明示的に宣言されている場合、WebSearch・WebFetch より宣言された手段を優先して使う。取得できなかった場合はその事実を明示した上で WebSearch・WebFetch にフォールバックする。明示宣言が無い場合は通常どおり WebSearch・WebFetch を使う。
- MUST: 答えを知っていると思っても、学習データだけで回答・計画しない (メインループ・subagent を問わない)。理由: 学習データは cutoff 以降の変更を含まず、古い仕様を自信を持って答える失敗に本人が気づけない。
  - 取得できなかった場合は取得不可の事実を伝え、該当箇所の回答・計画を保留する。
  - 取得結果が部分的 (オプション名・型は取れたがコード例が無い等) で、それらを組み合わせてコード例や手順を自分で構成する場合は、ドキュメント由来の事実と自分が構成した部分を回答内で区別して明示する。
  - 保留と構成の境界は、問われた事実そのもの (オプション名・引数・設定値・挙動等) が取得できたかで引く。取得済みと認定するのは、問われたシンボル (型・関数・オプション) 自体の本文または要約にその事実が書かれている場合に限る。別シンボルの記述からの類推は構成部分として区別表示する。WebFetch は取得ページの要約を返すため、要約に問われたシンボルが現れない場合は未取得として扱う。
- 対象は外部のライブラリ・ツール・サービスの仕様。コードベース内のシンボル・参照の調査 (lsp ルール) や grep による探索は本ルールの対象外。一般的なプログラミング概念・アルゴリズム・ビジネスロジックのデバッグ・コードレビューも対象外。
  - 適用の判定単位はタスクの種別ではなく、いま確定しようとしている個別の事実がライブラリ仕様 (API の引数・戻り値・設定値・挙動) かどうか。対象外のタスクの途中でライブラリ仕様に触れる必要が出たときは、取得するか、その仕様に依存しない言い方 (観測した事実・既存コードの形) に書き換えて取得を避けるかを選んでよい。
  - 取得が必須になるのは、仕様を断定して回答や計画の根拠にする場合に限る。断定かどうかは語調ではなく依存関係で決める。回答や計画の正否がその仕様の真偽に依存する書き方なら、「候補」「可能性」と弱めても断定として扱う。
- 同一の論点 (ライブラリと質問の組) について一度取得した結果は、同じ会話内で再利用してよい。取得済みの結果で足りるのに再取得しない。

## 情報源の優先順位

- MUST: 一次情報は次の順で当たり、上位で取得できた事実を採用する。
  1. 公式ドキュメントサイト (プロジェクトまたはベンダーが運営するもの)
  2. 公式リポジトリの README・release notes・CHANGELOG・リポジトリ内ドキュメント
  3. パッケージレジストリ (npm・PyPI・crates.io 等) のパッケージページ
- 第三者 (ブログ・Q&A サイト・個人リポジトリ) は補助に限る。一次情報に無い事実を第三者から採る場合は、回答内で第三者由来と明記し、仕様の断定の根拠にしない。
- WebSearch の結果は一次情報へ辿るための入口として使い、検索結果の要約を事実の根拠にしない。URL を特定したら WebFetch で本文を取得する。
- 公式ドメインが分からないときは、パッケージレジストリのページ (homepage・repository の欄) から辿る。

## バージョン

- MUST: 取得前に対象プロジェクトが固定しているバージョンを確認する (lockfile・マニフェスト・flake.lock 等)。そのバージョンのドキュメントを引き、URL のバージョンセグメント (`/v5/`・`/en/stable/`・タグ付き README 等) をバージョンに合わせる。
- バージョンが特定できない、またはバージョン別ページが無い場合は最新版を引き、回答内で「最新版 (バージョンの特定不可)」と明記する。
- 取得結果に unstable・pre-release・deprecated 等の注記があれば回答に含める。

## subagent へ委譲するときの扱い

- `research-worker` subagent は WebSearch・WebFetch を持つ。ライブラリ仕様の調査を `research-worker` へ委譲する場合、委譲プロンプトには次を含める。
  - ライブラリ名・対象のバージョン (分かる範囲)・英語で書いた具体的な質問文。質問文には問われるシンボル名を含める。
  - 情報源の優先順位 (上記) と、第三者は補助に限ること。
  - 返却物: 取得したドキュメントの要点、各要点の Source URL、取得したページのバージョン、unstable・pre-release 由来の注記 (無ければ「注記なし」と返させる)。取得結果に無い内容を補わせない (コード例が無ければ「無い」と返させる)。
  - 取得できなかった場合は、取得不可の事実とその理由 (エラーメッセージ・ページ未発見等) だけを返すこと。学習データで埋めない。
- MUST: 対象リポジトリの CLAUDE.md 等でライブラリ調査手段が明示宣言されている場合、委譲プロンプトは上記に代えて、宣言された手段の実体 (SKILL.md 等) を Read させ、その手順に従わせる。取得できなかった場合は上記の WebSearch・WebFetch の手順へフォールバックさせる。
- メインループは取得を自分で行わず、実行を `research-worker` へ委譲する (dev-workflow ルールの工程 2。`model` 等の起動パラメータも同ルールに従う)。同じ会話で取得済みの結果の再利用 (原則の最終項) はこの限りでなく、再取得自体が不要。
- `implementer` へ渡す実装計画にライブラリ仕様が関わる場合、その仕様は委譲前に確定して計画に書き下す。implementer に取得させない。
