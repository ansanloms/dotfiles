# 開発フロー (調査 → 計画 → 承認 → 隔離 → 実装委譲 → レビュー → コミット / PR → 片付け)

ファイル変更を伴うタスクの工程の順序と工程間の受け渡し、および subagent の運用を定めるルール。worktree・ドキュメント取得・コミット規約・レビューループの具体手順は各ルール・skill に委譲し、ここには転記しない。

メインループは判断 (設計・計画・承認取得・レビューの裁定・コミット/PR 文面の決定) だけを担い、読み取り・探索・実行・編集は subagent へ外出しする。Claude Code の呼び出しはステートレスな API 上で動き、ツール呼び出しごとにその時点の全コンテキストが再送されるため、コンテキストが育ったメインループが自分で手を動かすほど 1 リクエストの再送量が膨らむ。

| 役割                                                            | 担当                                                                                              |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 実装                                                            | implementer subagent (`~/.claude/agents/implementer.md`、sonnet)                                  |
| 調査                                                            | research-worker subagent (`~/.claude/agents/research-worker.md`、sonnet)                          |
| `/code-review` の実行                                           | code-review-runner subagent (`~/.claude/agents/code-review-runner.md`、既定 sonnet / 昇格時 opus) |
| 公開 (畳み込み・commit・push・PR 作成・branch description 更新) | pr-publisher subagent (`~/.claude/agents/pr-publisher.md`、haiku)                                 |

## 工程

工程 1〜3 は plan mode の中で行う。ファイル変更を伴う依頼を受けたら、最初に `EnterPlanMode` を呼ぶ (下記「plan mode」)。

1. **調査**: 変更内容の確定に必要な読み取りは research-worker へ委譲し、メインループは要点だけ受け取る。ライブラリ仕様は research ルール、コードベース内のシンボルは lsp ルールに従う。調査結果は計画に書き下し、implementer に調査から任せない。
2. **計画**: 会話文脈に依存しない自己完結した計画を作る。目的・対象ファイル・変更内容・制約・検証コマンド (実行 cwd = 隔離 worktree 直下を併記。該当ツールが無ければ「突合のみ」と明記) を含める。
   - 計画の冒頭に設計の分岐を置く。採りうる案を並べ、最も単純な案 (既存の仕組みに乗る・ファイルや依存を増やさない案) を必ず含め、推奨とその理由を書く。分岐が無ければ「分岐なし」と書く。
   - ユーザの答えで計画の中身が変わる分岐は、計画を詳細に書く前に `AskUserQuestion` で決める。理由: 2026-11-12 に集計した直近 26 セッションで、承認までに 3 往復以上かかった 5 セッションの往復は、承認の可否ではなく論点の追加と方針の選び直しだった。
   - 散文以外のファイルを含む計画には `/code-review` の level と天井を根拠付きで書く (判定条件と既定値は `review-loop` skill)。
   - 既存挙動を変える計画は、対象ファイルの既存テストの期待値と突合し、矛盾があればテストの扱いを明記する。
3. **承認**: `ExitPlanMode` で計画を提示し、承認を得てから工程 4 以降へ進む。
4. **隔離**: worktree ルールに従い、タスク専用ブランチを worktree に切る。複数の PR を並行して扱うときは PR ごとに worktree を切り、メインループはどの worktree にも入らずメイン checkout に留まり、subagent には各 worktree の絶対パスを渡して並列に起動する。理由: `EnterWorktree` で入ると隔離ガードが subagent にも及び、直列作業になる (worktree ルール)。
5. **実装**: implementer へ計画を渡して委譲する。委譲の最後に WIP コミットをさせる (文言は `review-loop` skill)。
6. **レビュー**: 下記「レビュー」に従う。
7. **コミット / PR**: 既定はコミット・push・PR 作成まで。コミットのみで止めるのはユーザ指示がある場合に限る。
   - WIP コミットは push 前に 1 つに畳む (手順は `review-loop` skill)。
   - コミットメッセージ・PR 本文・branch description の文面はメインループが決める (コミット規約は git ルール)。実行 (畳み込み・commit・push・PR 作成・branch description 更新) は文面を添えて pr-publisher へ 1 回で委譲する。branch description は PR URL の位置だけプレースホルダにした全文を渡し、pr-publisher が PR 作成の戻り値で置換して設定する (書式は worktree ルール)。理由: URL を受け取ってから再委譲する往復を省く。置換は判断を伴わない。
   - pr-publisher に渡すのは内容が変わらない作業だけ。main への rebase やレビュー指摘の反映で内容が変わる作業は implementer に任せ、検証と WIP コミットまで持たせてから pr-publisher へ渡す。委譲文でこの境界を明示する。
   - pr-publisher が失敗 (push の拒否・衝突・`gh` の失敗) を報告したら、メインループが原因を判断して implementer への再委譲かユーザへの確認に振り分ける。pr-publisher に直させない。
8. **片付け**: マージ報告を受けたら worktree ルールの片付け手順に従う。

## plan mode

工程 1〜3 を plan mode で行う理由は 2 つある。承認前の書き込みをハーネスが止めること、承認の問いが専用の UI で出て計画ファイルが残ることである。

- plan mode の間は、メインループも起動した subagent も読み取り専用になる。隔離 (工程 4) を承認の後に置くのはこのためである。
- 承認前に worktree が要る場合は、`EnterPlanMode` より先に用意する。該当するのは次の 2 つである。
  - 別ブランチを読み取りで調べる調査 (worktree ルール)
  - ユーザが下書きを書く場所が要る場合 (hands-on ルール)
- 計画を練り直すときは plan mode に留まる。ユーザが計画を退けた、または論点を足した場合は、計画ファイルを書き直してから `ExitPlanMode` を呼び直す。
- 承認後に計画の中身を変える必要が出たら (レビューでの設計変更を除く)、`EnterPlanMode` で入り直して再承認を取る。
- 下記「例外」の作業と、ファイルを変更しない依頼 (質問・調査) では plan mode に入らない。例外の作業は、計画を応答文で提示して承認を取る。
- `EnterPlanMode` が使えない環境では、同じ順序を plan mode なしで踏み、その事実を報告に書く。

## 運用

- 前提: メインセッションは Fable で走らせる。
- MUST: subagent のモデルは呼び出し側が決める。frontmatter に `model:` を持つ agent (implementer・research-worker・code-review-runner・pr-publisher) はそれに従い、それ以外 (general-purpose・Explore・Plan 等) を起動するときは `model` を必ず渡す。
  - 深い読み取り・検証 = `opus`、機械的な探索・実行 = `sonnet`。`fable` は指定しない。
  - `fork` は使わない。理由: 親モデルを継承する。
- メインループが直接打つツールと、subagent へ委譲する作業は、回数ではなく作業の種類で分ける。
  - 直接打つ作業は次のとおり。
    - 委譲とその受け取り
    - ユーザへの提示 (手段は nvim ルール)
    - 対象が分かっている単発の事実確認 (ファイル 1 つの該当箇所、コマンド 1 つの結果)
    - 他のルール・skill がメインループの責務と定める手順。nvim の socket 解決、worktree の用意と branch description、`review-loop` の台帳の読み書きと r2 以降の突合、`gh` での状態確認が当たる。
    - 下記「例外」の作業
  - 委譲する作業は次のとおり。
    - どこに何があるか分からない探索
    - 複数ファイルにまたがる読み取り
    - 長い出力を返すコマンド (ログ・diff 全文・テスト出力)
    - ライブラリ仕様の取得
    - ファイル変更を伴う実装
  - 委譲にも費用がある。subagent は 1 回の起動で数万 token を使う (code-review-runner は 1 回 55〜63k)。
    - 対象が分かっている 1 回の読み取りは委譲しない。
    - 独立した調査は 1 回の委譲文にまとめるか、並列に起動する。
  - 理由: 以前は「直接のツール呼び出しを 2 回以上続けない」と回数で縛っていたが、直近 26 セッション中 24 セッションで破られていた。直接打った Bash の約 6 割は worktree と台帳の操作で、ルール自身が課した手順だった (2026-11-12 集計)。
- MUST: ファイル変更を伴う実装はメインループが直接行わず implementer へ委譲する。この委譲義務はメインループにのみ課す。subagent として動いている場合 (implementer 自身を含む) は再委譲せず直接行う。
- WIP コミットはレビュー中に implementer が行う唯一のコミットで、工程 7 の畳み込み前に push しない。
- MUST: 検証 (lint・test・build・型検査等) は内容が最後に変わった後に 1 回行う。内容が変わらない公開作業 (畳み込み・push・PR 作成・branch description 更新) では再実行しない。理由: 畳み込みは既に検証済みのツリーをそのまま指し直すだけで、CI が同じ検証を重ねる。レビュー指摘の反映や main への rebase で内容が変わったときは implementer が検証と WIP コミットまで持つ。委譲文に「検証を通す」を書くのは内容を変える委譲に限る。

## レビュー

implementer の完了報告後、`review-loop` skill の手順でラウンドを回す。skill には `ledger` (作業ファイル)、`repo`、`base`、`branch` と、正本 `git config branch.<branch>.review` への `load`・`store` を渡す (供給の形は skill の「受け取り」節)。

- MUST: 各ラウンドは (1) メインループ自身による計画との突合と (2) code-review-runner 経由の `/code-review` の 2 段で行う。
  - `/code-review` を Skill ツールで直接起動しない。理由: オーケストレータが Fable を継承する。
  - runner へ渡すのは range と level だけで、前提・不採用事項・台帳は reviewer に届かない (`/code-review` の fork は呼び出し元の文脈を継承しない)。
- MUST: 採用した指摘の修正が設計変更 (定義は skill) に当たれば、再委譲せず計画の before/after を提示して再承認を取る。修正の再委譲に追加承認は要らない。
- MUST: 終了は skill の終了条件で判定する。収束せず設計を書き直す場合と、同じ指摘が再委譲 2 回で残る場合はユーザへ判断を仰ぐ。cut-off はレビューしていない修正を報告に明示する。
- MUST: 裁定を出した直後に台帳へ書く。指摘は裁定 (採用/不採用/ユーザ判断とその理由) を添えて全件開示する。不採用を省かない。
  - 台帳と照合して既知 (`不採用`/`ユーザ判断` と同じ症状) と判定した指摘は再裁定せず、その旨と元の裁定を開示する。
  - 変更が持ち込んでいない指摘 (base の時点で同じ症状が出るもの) は `範囲外 (既存)` として裁定と分けて開示し、終了の判定に数えない。理由: 不採用の行に埋もれた指摘を後から拾い直すと、PR の範囲がレビューを通らずに広がる。
    - その PR では直さない。行き先は工程 7 の報告でまとめて 1 回聞く (判定基準・選択肢・手順は skill)。
    - この PR で対応すると決まったら、計画の変更として再承認を取る。
  - 0 件ならその事実を、実行しなかったなら事実と一次根拠を報告する。
  - branch description に `## review` 節を置かない (status への 1 行反映は skill)。

## 例外

diff 全体 (変更するファイルすべて) が次のいずれかに該当する作業は、メインループが直接行ってよく、上記「運用」の委譲の分担と「レビュー」の 2 段・WIP コミット・台帳を適用しない。理由: 委譲オーバーヘッドが勝る。判定に迷う場合は例外を適用せず通常フローに倒す。

- 単一ファイルかつ 5 行以内で、挙動の意味変更を伴わない修正 (typo・設定値 1 箇所等)
- 意味変更を伴わない同一パターンの機械的置換 (件数・行数を問わない)
- 散文の文書 (ルール・CLAUDE.md・skill 本文・agent 定義・README 等) の執筆・改稿。
  - 散文以外のファイル (ソース・設定・データ) を 1 ファイルでも含めば該当しない。散文中のコマンド例・コードフェンスは散文の一部。
  - 文書のみでも計画と本文が分離できるもの (既定値の一括差し替え等) は除く。

例外経路でも工程 1〜4 と 7〜8 は踏む (plan mode には入らず、計画は応答文で提示する)。工程 7 の実行は例外経路でも pr-publisher へ委譲する。コミット前に diff は提示しない。変更したファイルと変更の要点を報告に書き、これを通常フローの「レビュー」1 の突合に代える。報告と工程 7 の委譲は同じターンで続けて発行してよい。`/code-review` を実行しなかった事実とその根拠 (この例外) は報告に含める。
