# 開発フロー (隔離 → 調査 → 計画 → 承認 → 実装委譲 → レビュー → コミット / PR → 片付け)

ファイル変更を伴うタスクの工程の順序と工程間の受け渡し、および subagent の運用を定めるルール。worktree・ドキュメント取得・コミット規約の具体手順は各ルール・skill に委譲し、ここには転記しない。

メインループは判断 (設計・計画・承認取得・レビューの裁定・コミット / PR 文面の決定) だけを担い、読み取り・探索・実行・編集は subagent へ外出しする。Claude Code はツール呼び出しごとにその時点の全コンテキストを再送するため、コンテキストが育ったメインループが自分で手を動かすほど 1 リクエストの再送量が膨らむ。

| 役割 | 担当 |
| --- | --- |
| 実装 | implementer subagent (`.claude/agents/implementer.md`、sonnet) |
| 調査 | research-worker subagent (`.claude/agents/research-worker.md`、sonnet) |
| `/code-review` の実行 | code-review-runner subagent (`.claude/agents/code-review-runner.md`、opus) |

## 工程

1. **隔離**: worktree ルールに従い、タスク専用ブランチを worktree に切る。
2. **調査**: 変更内容の確定に必要な読み取りは research-worker へ委譲し、メインループは要点だけ受け取る。ライブラリ仕様は research ルール、コードベース内のシンボルは lsp ルールに従う。調査結果は計画に書き下し、implementer に調査から任せない。
3. **計画**: 会話文脈に依存しない自己完結した計画を作る。目的・対象ファイル・変更内容・制約・検証コマンド (実行 cwd = 隔離 worktree 直下を併記。該当ツールが無ければ「突合のみ」と明記) を含める。散文以外のファイルを含む計画には `/code-review` の level と根拠も書く。既存挙動を変える計画は、対象ファイルの既存テストの期待値と突合し、矛盾があればテストの扱いを明記する。
4. **承認**: 計画をユーザに提示し、承認を得てから工程 5 以降へ進む。工程 1〜2 は可逆または読み取りのみなので承認前に行ってよい。
5. **実装**: implementer へ計画を渡して委譲する (コミットはさせない)。
6. **レビュー**: 下記「レビュー」の 2 段で行い、指摘を全件開示する。
7. **コミット / PR**: 既定はコミット・push・PR 作成まで。コミットのみで止めるのはユーザ指示がある場合に限る。コミットメッセージと PR 本文はメインループが決め (コミット規約は git ルール)、実行 (add / commit / push / PR 作成) は文面を添えて implementer へ委譲する。PR URL を受け取ったら branch description を更新する (worktree ルール)。
8. **片付け**: マージ報告を受けたら worktree ルールの片付け手順に従う。

## 運用

- 前提: メインセッションは Fable で走らせる。
- MUST: subagent のモデルは呼び出し側が決める。frontmatter に `model:` を持つ agent (implementer / research-worker / code-review-runner) はそれに従い、それ以外 (general-purpose / Explore / Plan 等) を起動するときは `model` を必ず渡す。深い読み取り・検証 = `opus`、機械的な探索・実行 = `sonnet`。`fable` は指定しない。`fork` は親モデルを継承するので使わない。PreToolUse hook (`.claude/scripts/subagent-model.ts`) が未指定に `opus` を補うが、安全網であって明示義務の代わりではない。
- MUST: メインループの直接のツール呼び出しは (a) 委譲とその受け取り、(b) ユーザへの提示 (手段は nvim ルール)、(c) 1 コマンドで済む単発の事実確認、に限る。Bash / Read / Edit / Write / LSP を 2 回以上続けて打つ状態になったら、その作業を subagent へ切り出す。下記「例外」、下記「レビュー」1 の diff 取得、他のルール・skill がメインループの責務と定める手順 (nvim の socket 解決、worktree の用意と branch description) は対象外。
- MUST: ファイル変更を伴う実装はメインループが直接行わず implementer へ委譲する。この委譲義務はメインループにのみ課す。subagent として動いている場合 (implementer 自身を含む) は再委譲せず直接行う。
- メインループはツールを打つ前にこの分担に反していないか確認する。

## レビュー

implementer の完了報告後、メインループは次の 2 段で行う。対象 diff は、委譲前の基点との差分 (未コミットなら HEAD との diff、コミット済みならベースブランチとの diff)。

1. **計画との突合**: メインループ自身が diff を読み、実装漏れ・計画外の変更が無いかを照合し、implementer が報告した検証結果を確認する (diff 自体のユーザ提示は要らない)。
2. **`/code-review`**: code-review-runner を Agent で起動し、対象 (未コミットなら隔離 worktree の絶対パス、コミット済みならブランチ名。メインセッションが対象リポジトリ外ならリポジトリの絶対パスも添える) と level を渡す。MUST: メインループは `/code-review` を Skill ツールで直接起動しない (オーケストレータが Fable を継承する)。
   - level: 既定 `medium`。変更がセキュリティ・認証・並行制御 (ロック・タイマー・並列 I/O)・削除や上書きに関わるか、複数モジュール (パッケージ境界。無ければトップレベルディレクトリ。ルート直下のファイルはまとめて 1 モジュール) に広がる diff は `high`。迷ったら `high`。低く走らせたと後で気づいたら、得られた指摘はそのまま使い、次の再レビューから正しい level にする。
   - 返却の判別: 指摘ごとにファイルと行 (または関数)・要約・失敗シナリオが付いて列挙されていれば生。総評の散文だけ、件数と列挙数の食い違い、採用 / 不採用等の裁定語付き、のいずれかなら加工とみなし、同じ内容で runner を 1 回だけ取り直す。取り直しても加工されていたら「加工済み」と明記してユーザへ判断を仰ぐ。Agent の `description` は `code-review` / `code-review retry` / `code-review 2nd` のように回数を含める。
   - 裁定はメインループが行い、修正は implementer へ再委譲する。再委譲後も同じ 2 段を、初回の委譲前基点からの累積 diff に対して行う。1 つの指摘がその指摘への再委譲 2 回で解消しなければ打ち切り、残存指摘・試行回数・作業ツリーの状態・選択肢 (計画の書き換えと再承認 / 明示承認を得た追加再委譲 / ユーザ指示によるメインループの直接修正 / 撤回) を添えてユーザへ判断を仰ぐ。指摘の同一性は「同じ入力でどう壊れるか」で判定し、関数の分割・改名・移動では別扱いにしない。ユーザ判断で計画を改めたらカウントを仕切り直す。
   - 散文の文書のみの diff は 1 の突合のみでよい。
- MUST: `/code-review` の指摘は、裁定 (採用 / 不採用とその理由) を添えて全件開示する。不採用を省かない。0 件ならその事実を、実行しなかったなら事実と一次根拠を報告する。承認済み計画の範囲内の修正再委譲に追加承認は要らない。計画自体を書き換える場合は再承認を取る。

## 例外

diff 全体 (変更するファイルすべて) が次のいずれかに該当する作業は委譲オーバーヘッドが勝るため、メインループが直接行ってよく、「直接のツール呼び出し」の MUST と上記「レビュー」の 2 段を適用しない。判定に迷う場合は例外を適用せず通常フローに倒す。

- 単一ファイルかつ 5 行以内で、挙動の意味変更を伴わない修正 (typo・設定値 1 箇所等)
- 意味変更を伴わない同一パターンの機械的置換 (件数・行数を問わない)
- 散文の文書 (ルール・CLAUDE.md・skill 本文・agent 定義・README 等) の執筆・改稿。散文以外のファイル (ソース・設定・データ) を 1 ファイルでも含めば該当しない。散文中のコマンド例・コードフェンスは散文の一部。文書のみでも計画と本文が分離できるもの (既定値の一括差し替え等) は除く。

例外経路でも工程 1〜4 と 7〜8 は踏む。工程 7 の実行は例外経路でも implementer へ委譲する。コミット前に diff をユーザへ提示する (通常フローの「レビュー」1 の突合に代わるもの)。これは報告であり承認待ちにはしないため、提示と工程 7 の委譲は同じターンで続けて発行してよい。`/code-review` を実行しなかった事実とその根拠 (この例外) は報告に含める。
