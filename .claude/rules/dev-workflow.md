# 開発フロー (隔離 → 調査 → 計画 → 承認 → 実装委譲 → レビュー → コミット / PR → 片付け)

ファイル変更を伴うタスクの工程の順序と工程間の受け渡し、および subagent の運用を定めるルール。worktree・ドキュメント取得・コミット規約・レビューループの具体手順は各ルール・skill に委譲し、ここには転記しない。

メインループは判断 (設計・計画・承認取得・レビューの裁定・コミット/PR 文面の決定) だけを担い、読み取り・探索・実行・編集は subagent へ外出しする。Claude Code の呼び出しはステートレスな API 上で動き、ツール呼び出しごとにその時点の全コンテキストが再送されるため、コンテキストが育ったメインループが自分で手を動かすほど 1 リクエストの再送量が膨らむ。

| 役割                  | 担当                                                                       |
| --------------------- | -------------------------------------------------------------------------- |
| 実装                  | implementer subagent (`.claude/agents/implementer.md`、sonnet)             |
| 調査                  | research-worker subagent (`.claude/agents/research-worker.md`、sonnet)     |
| `/code-review` の実行 | code-review-runner subagent (`.claude/agents/code-review-runner.md`、opus) |

## 工程

1. **隔離**: worktree ルールに従い、タスク専用ブランチを worktree に切る。複数の PR を並行して扱うときは PR ごとに worktree を切り、メインループはどの worktree にも入らずメイン checkout に留まり、subagent には各 worktree の絶対パスを渡して並列に起動する。理由: `EnterWorktree` で入ると隔離ガードが subagent にも及び、直列作業になる (worktree ルール)。
2. **調査**: 変更内容の確定に必要な読み取りは research-worker へ委譲し、メインループは要点だけ受け取る。ライブラリ仕様は research ルール、コードベース内のシンボルは lsp ルールに従う。調査結果は計画に書き下し、implementer に調査から任せない。
3. **計画**: 会話文脈に依存しない自己完結した計画を作る。目的・対象ファイル・変更内容・制約・検証コマンド (実行 cwd = 隔離 worktree 直下を併記。該当ツールが無ければ「突合のみ」と明記) を含める。
   - 散文以外のファイルを含む計画には `/code-review` の level と天井を根拠付きで書く (判定条件と既定値は `review-loop` skill)。
   - 既存挙動を変える計画は、対象ファイルの既存テストの期待値と突合し、矛盾があればテストの扱いを明記する。
4. **承認**: 計画をユーザに提示し、承認を得てから工程 5 以降へ進む。工程 1〜2 は可逆または読み取りのみなので承認前に行ってよい。
5. **実装**: implementer へ計画を渡して委譲する。委譲の最後に WIP コミットをさせる (文言は `review-loop` skill)。
6. **レビュー**: 下記「レビュー」に従う。
7. **コミット / PR**: 既定はコミット・push・PR 作成まで。コミットのみで止めるのはユーザ指示がある場合に限る。
   - WIP コミットは push 前に 1 つに畳む (手順は `review-loop` skill)。
   - コミットメッセージと PR 本文はメインループが決める (コミット規約は git ルール)。実行 (畳み込み・commit・push・PR 作成) は文面を添えて implementer へ委譲する。
   - PR URL を受け取ったら branch description を更新する (worktree ルール)。
8. **片付け**: マージ報告を受けたら worktree ルールの片付け手順に従う。

## 運用

- 前提: メインセッションは Fable で走らせる。
- MUST: subagent のモデルは呼び出し側が決める。frontmatter に `model:` を持つ agent (implementer・research-worker・code-review-runner) はそれに従い、それ以外 (general-purpose・Explore・Plan 等) を起動するときは `model` を必ず渡す。
  - 深い読み取り・検証 = `opus`、機械的な探索・実行 = `sonnet`。`fable` は指定しない。
  - `fork` は使わない。理由: 親モデルを継承する。
  - PreToolUse hook (`.claude/scripts/subagent-model.ts`) が未指定に `opus` を補うが、安全網であって明示義務の代わりではない。
- MUST: メインループの直接のツール呼び出しは (a) 委譲とその受け取り、(b) ユーザへの提示 (手段は nvim ルール)、(c) 1 コマンドで済む単発の事実確認、に限る。Bash・Read・Edit・Write・LSP を 2 回以上続けて打つ状態になったら、その作業を subagent へ切り出す。下記「例外」と、他のルール・skill がメインループの責務と定める手順 (nvim の socket 解決、worktree の用意と branch description、`review-loop` の突合用 diff 取得と台帳の読み書き) は対象外。
- MUST: ファイル変更を伴う実装はメインループが直接行わず implementer へ委譲する。この委譲義務はメインループにのみ課す。subagent として動いている場合 (implementer 自身を含む) は再委譲せず直接行う。
- WIP コミットはレビュー中に implementer が行う唯一のコミットで、工程 7 の畳み込み前に push しない。
- MUST: メインループはツールを打つ前にこの分担に反していないか確認する。

## レビュー

implementer の完了報告後、`review-loop` skill の手順でラウンドを回す。skill には `ledger` (作業ファイル)、`repo`、`base`、`branch` と、正本 `git config branch.<branch>.review` への `load`・`store` を渡す (供給の形は skill の「受け取り」節)。

- MUST: 各ラウンドは (1) メインループ自身による計画との突合と (2) code-review-runner 経由の `/code-review` の 2 段で行う。
  - `/code-review` を Skill ツールで直接起動しない。理由: オーケストレータが Fable を継承する。
  - runner へ渡すのは range と level だけで、前提・不採用事項・台帳は reviewer に届かない (`/code-review` の fork は呼び出し元の文脈を継承しない)。
- MUST: 採用した指摘の修正が設計変更 (定義は skill) に当たれば、再委譲せず計画の before/after を提示して再承認を取る。修正の再委譲に追加承認は要らない。
- MUST: 終了は skill の終了条件で判定する。収束せず設計を書き直す場合と、同じ指摘が再委譲 2 回で残る場合はユーザへ判断を仰ぐ。cut-off はレビューしていない修正を報告に明示する。
- MUST: 裁定を出した直後に台帳へ書く。指摘は裁定 (採用/不採用/ユーザ判断とその理由) を添えて全件開示する。不採用を省かない。
  - 台帳と照合して既知 (`不採用`/`ユーザ判断` と同じ症状) と判定した指摘は再裁定せず、その旨と元の裁定を開示する。
  - 0 件ならその事実を、実行しなかったなら事実と一次根拠を報告する。
  - branch description に `## review` 節を置かない (status への 1 行反映は skill)。

## 例外

diff 全体 (変更するファイルすべて) が次のいずれかに該当する作業は、メインループが直接行ってよく、「直接のツール呼び出し」の MUST と上記「レビュー」の 2 段・WIP コミット・台帳を適用しない。理由: 委譲オーバーヘッドが勝る。判定に迷う場合は例外を適用せず通常フローに倒す。

- 単一ファイルかつ 5 行以内で、挙動の意味変更を伴わない修正 (typo・設定値 1 箇所等)
- 意味変更を伴わない同一パターンの機械的置換 (件数・行数を問わない)
- 散文の文書 (ルール・CLAUDE.md・skill 本文・agent 定義・README 等) の執筆・改稿。
  - 散文以外のファイル (ソース・設定・データ) を 1 ファイルでも含めば該当しない。散文中のコマンド例・コードフェンスは散文の一部。
  - 文書のみでも計画と本文が分離できるもの (既定値の一括差し替え等) は除く。

例外経路でも工程 1〜4 と 7〜8 は踏む。工程 7 の実行は例外経路でも implementer へ委譲する。コミット前に diff は提示しない。変更したファイルと変更の要点を報告に書き、これを通常フローの「レビュー」1 の突合に代える。報告と工程 7 の委譲は同じターンで続けて発行してよい。`/code-review` を実行しなかった事実とその根拠 (この例外) は報告に含める。
