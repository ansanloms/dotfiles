# 開発フロー (隔離 → 調査 → 計画 → 承認 → 実装委譲 → レビュー → コミット / PR → 片付け)

ファイル変更を伴うタスクを進める工程の順序と、工程間の受け渡し (計画に何を書くか・レビューをどう段取るか・何をユーザへ開示するか) を定めるルール。各工程の具体手順 (worktree の切り方・ドキュメントの取り方・コミット規約等) は既存のルール・skill に委譲し、本ルールから転記しない。

メインループは設計・判断・レビューの裁定を担い、ツール呼び出し密度の高い実装作業は implementer subagent (`.claude/agents/implementer.md`、model: sonnet) へ委譲する。実装結果の正当性レビューは Claude Code 組み込みの `/code-review` skill で行う。

## 背景

- メインループと implementer でモデルを分けるのは判断品質と実行コストの分担のため。メインループは Fable で走らせて設計・裁定の品質を確保し、実装の実行自体は計画が確定していれば Sonnet で足りる。
- 正当性レビューを `/code-review` skill に任せるのは、fresh-context のレビューエージェント群と指摘の検証パスを持ち、自前 reviewer subagent の上位互換であるため (メンテナンスも Anthropic 側で行われる)。一方「計画どおりに実装されたか」の照合は、計画の作者であるメインループが直接行う。照合には作者知識が有利に働くためで、作者バイアスが問題になるのは計画自体の良否判断だが、計画自体の欠陥も実害があれば /code-review がバグとして検出する。(以前は独立レビューを reviewer subagent (`.claude/agents/reviewer.md`) へ委譲していたが、上記の理由で /code-review へ移行し、reviewer は廃止した。)
- このルールは当初 `model-split` (モデル分担) として導入したが、内容は分担という手段ではなく開発フロー全体の順序と受け渡しを縛るものだったため、縛る対象の名前に改めた。

## 工程

1. **隔離**: メインの worktree のブランチを切り替えず、タスク専用ブランチを worktree に切る。判断基準・配置先・branch description の扱いは worktree ルールに従う。
2. **調査**: 変更内容の確定に必要な読み取りはメインループが行う。ライブラリ仕様は research ルール (`find-docs`)、コードベース内のシンボル・参照は lsp ルールに従う。調査結果は計画に書き下し、implementer に調査から任せない。
3. **計画**: 自己完結した計画を作る。目的・対象ファイル・変更内容・制約 (規約等)・検証コマンドを含め、会話の文脈を前提にしない。検証コマンドは成果物に合わせる (コードならテスト・型チェック一式、ドキュメントのみなら lint / format、該当ツールが無ければ「突合のみ」と計画に明記)。
4. **承認**: 計画をユーザに提示し、承認を得てから実装に進む。提示・承認の取り方は CLAUDE.md の原則に従う。本ルールが定めるのは順序 (承認は計画の後・実装の前) のみ。
5. **実装**: implementer subagent へ委譲する (下記「運用」)。
6. **レビュー**: 計画との突合と `/code-review` の 2 段で行い、指摘をユーザへ開示する (下記「運用」)。
7. **コミット / PR**: メインループの管轄とし、git ルール (コミット規約) に従う。PR 作成は worktree ルールが定める branch description 更新の節目でもある。
8. **片付け**: マージ報告を受けたら worktree ルールの片付け手順に従う。

## 運用

- 前提: メインセッションは Fable で走らせる (`/model fable` または settings の `model`)。
- MUST: ファイル変更を伴う実装作業は、メインループが直接行わず implementer subagent へ委譲する。
- この委譲 MUST はメインセッション (メインループ) にのみ適用する。本ルールは subagent のコンテキストにも配られるが、subagent として動いている場合 (implementer 自身を含む) は再委譲せず、与えられた作業を直接行う。implementer が Agent 系ツールを持たないのはこの再帰を機械的に防ぐためであり、委譲できないことは異常ではない。
- MUST: 委譲時は工程 3 の自己完結した計画を渡す。変更内容の調査・確定 (読み取り) はメインループが行って結果を計画に書き下し、implementer に調査から任せない。
- MUST: 既存挙動の変更を伴う計画は、委譲前に対象ファイルへ紐づく既存テストの期待値と変更内容を突合する。矛盾がある場合は、既存テストの扱い (更新可否・更新内容) を計画に明記してから委譲する。怠ると implementer は計画外の判断を禁じられているため機械的に差し戻すしかなく、往復コストだけが残る。
- MUST: implementer の完了報告後、メインループは次の 2 段でレビューする。レビュー対象の diff は、implementer の変更が乗った作業ツリーと委譲前の基点との差分 (未コミットなら HEAD との diff、コミット済みならベースブランチとの diff) とする。
  1. 計画との突合: メインループ自身が diff を読み、計画項目の実装漏れ・計画外の変更が無いかを照合する。implementer が報告した検証コマンドの実行結果もここで確認する。
  2. `/code-review` の実行: diff を対象に code-review skill を実行する。既定は medium。セキュリティ・認証・並行性・データ損失の可能性に触れる diff、または変更が複数モジュールへ広がる diff は high に上げる。`--fix` は使わない。
     指摘の裁定はメインループが行い、修正が必要なら implementer へ再委譲する。再委譲で得た修正 diff にも同じ 2 段レビューを適用する。その際の diff 基点は初回の委譲前基点に固定する (修正分だけでなく累積 diff を見る)。打ち切りは指摘ごとに数え、1 つの指摘がその指摘に対する再委譲 2 回で解消しなければ反復を打ち切り、ユーザへ判断を仰ぐ。ドキュメントのみの diff では正当性レビューの効果が薄いため、(1) の突合のみでよい。
- MUST: `/code-review` の指摘は、メインループの裁定 (採用 / 不採用とその理由) を添えて全件ユーザへ開示する。不採用にした指摘を省かない。指摘が 0 件だった場合もその事実を報告する。裁定した修正の再委譲は開示と並行して進めてよいが、開示を省いて修正だけを報告しない。
- 例外: 次のいずれかに該当する作業は委譲オーバーヘッドが勝るため、メインループが直接行ってよく、2 段レビューも不要。判定に迷う場合は例外を適用せず通常フロー (委譲 + 2 段レビュー) に倒す。
  - 単一ファイルかつ変更 5 行以内の修正 (typo・設定値 1 箇所等)
  - 意味変更を伴わない同一パターンの機械的置換 (件数・行数を問わない)
  - 散文の文書 (ルール・CLAUDE.md・skill 本文・agent 定義・README 等) の執筆・改稿。自己完結した計画に変更内容を書き下すことが本文を書くことと等価になり、委譲しても転記の往復しか残らないため。コードを含む変更、または文書でも計画と本文が分離できるもの (既定値の一括差し替え等) はこの例外に含めない。
- メインループ側の委譲義務の強制力は instruction レベルであり機械的な enforcement は無い。メインループはファイル編集の前に、この分担に反していないか確認する。
