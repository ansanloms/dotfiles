# 開発フロー (隔離 → 調査 → 計画 → 承認 → 実装委譲 → レビュー → コミット / PR → 片付け)

ファイル変更を伴うタスクを進める工程の順序と、工程間の受け渡し (計画に何を書くか・レビューをどう段取るか・何をユーザへ開示するか) を定めるルール。各工程の具体手順 (worktree の切り方・ドキュメントの取り方・コミット規約等) は既存のルール・skill に委譲し、本ルールから転記しない。

メインループは設計・計画・承認取得・レビューの裁定・コミット文面の決定といった判断を担い、それ以外の作業 (読み取り・探索・実行・編集) は subagent へ外出しする。実装は implementer subagent (`.claude/agents/implementer.md`、model: sonnet)、調査は research-worker subagent (`.claude/agents/research-worker.md`、model: sonnet) へ委譲する。実装結果の正当性レビューは Claude Code 組み込みの `/code-review` skill で行う。

## 背景

- メインループと subagent でモデルを分けるのは判断品質と実行コストの分担のため。Fable はメインループ専用とし、設計・裁定の品質をそこで確保する。subagent は判断をしない前提なので sonnet / opus で足り、Fable を使わない。モデルは呼び出し側が明示する (下記「運用」)。
- メインループを判断に限定するのはトークン消費の構造による。Claude Code はツール呼び出し 1 回ごとにその時点の全コンテキストを API へ再送するため、コンテキストが育ったメインループが Bash / Read / Edit を打つたびに、その全量が課金される。2026-08-23 の transcript 集計 (8/15〜8/23、4557 リクエスト) では、メインループの自前作業 (Bash / Read / Edit / Write) が全消費の 35%、subagent が 48% (うち Fable を継承した general-purpose の fan-out が 17%、`/code-review` 起因が 24%) を占めた。同じ作業を subagent (固定コスト 30〜45K + 自分の履歴のみ) に移せば 1 リクエストあたりの再送量が数分の一になる。
- 正当性レビューを `/code-review` skill に任せるのは、fresh-context のレビューエージェント群と指摘の検証パスを持ち、自前 reviewer subagent の上位互換であるため (メンテナンスも Anthropic 側で行われる)。一方「計画どおりに実装されたか」の照合は、計画の作者であるメインループが直接行う。照合には作者知識が有利に働くためで、作者バイアスが問題になるのは計画自体の良否判断だが、計画自体の欠陥も実害があれば /code-review がバグとして検出する。(以前は独立レビューを reviewer subagent (`.claude/agents/reviewer.md`) へ委譲していたが、上記の理由で /code-review へ移行し、reviewer は廃止した。)
- このルールは当初 `model-split` (モデル分担) として導入したが、内容は分担という手段ではなく開発フロー全体の順序と受け渡しを縛るものだったため、縛る対象の名前に改めた。

## 工程

1. **隔離**: メインの worktree のブランチを切り替えず、タスク専用ブランチを worktree に切る。判断基準・配置先・branch description の扱いは worktree ルールに従う。
2. **調査**: 変更内容の確定に必要な読み取りは research-worker subagent へ委譲し、メインループは返却された要点だけを読む。ライブラリ仕様は research ルール (`find-docs`)、コードベース内のシンボル・参照は lsp ルールに従う (research-worker は LSP ツールを持つ)。メインループが直接 Read / Bash / LSP を打つのは、委譲の往復より明らかに小さい単発の事実確認 (1 コマンドで済み、結果を読んで次の判断に進めるもの) に限る。調査結果は計画に書き下し、implementer に調査から任せない。
3. **計画**: 自己完結した計画を作る。目的・対象ファイル・変更内容・制約 (規約等)・検証コマンドを含め、会話の文脈を前提にしない。検証コマンドは成果物に合わせる (コードならテスト・型チェック一式、ドキュメントのみなら lint / format、該当ツールが無ければ「突合のみ」と計画に明記)。検証コマンドには実行 cwd (隔離 worktree 直下) を併記する。リポジトリ設定が worktree 配置先を除外していると、メインから実行した一括検査が黙って素通りするため。コードを含む計画には `/code-review` の level とその根拠 (下記「運用」の判定基準による) も項目として含め、委譲前に確定させる。
4. **承認**: 計画をユーザに提示し、承認を得てから実装に進む。提示・承認の取り方は CLAUDE.md の原則に従う。本ルールが定めるのは順序のみで、承認の境界は工程 5 以降 (ファイル編集・委譲・コミット) の前に引く。工程 1 (隔離) と 2 (調査) は承認前に行ってよい。隔離は可逆で `git status` を汚さない準備、調査は読み取りであり、いずれも CLAUDE.md が言う「着手」に当たらない。
5. **実装**: implementer subagent へ委譲する (下記「運用」)。
6. **レビュー**: 計画との突合と `/code-review` の 2 段で行い、指摘をユーザへ開示する (下記「運用」)。
7. **コミット / PR**: コミットメッセージ・PR 本文の決定はメインループの管轄とし、git ルール (コミット規約) に従う。実行 (add / commit / push / PR 作成) は決めた文面を添えて implementer へ委譲し、文面をそのまま使わせる。PR 作成は worktree ルールが定める branch description 更新の節目でもある。
8. **片付け**: マージ報告を受けたら worktree ルールの片付け手順に従う。

## 運用

- 前提: メインセッションは Fable で走らせる (`/model fable` または settings の `model`)。Fable を使うのはメインループだけで、subagent には使わない。
- MUST: メインループの直接のツール呼び出しは次に限る。(a) 委譲とその受け取り (Agent / Skill / SendMessage / TaskOutput 等)、(b) ユーザへの提示 (nvim への送り出しを含む)、(c) 単発の事実確認 (1 コマンドで済み、結果を読んで次の判断に進めるもの)。Bash / Read / Edit / Write / LSP を 2 回以上続けて打つ状態 (自分で手を動かしている状態) になったら、その作業を subagent へ切り出す。調査は research-worker、実装・実行は implementer へ。
- MUST: subagent のモデルは呼び出し側が決める。frontmatter に `model:` を持つ agent (implementer = sonnet、research-worker = sonnet) はそれに従い、それ以外の種別 (general-purpose / Explore / Plan / claude-code-guide 等) を Agent で起動するときは `model` 引数を必ず渡す。値は用途で選ぶ: レビュー・検証・設計材料となる深い読み取り = `opus`、機械的な探索・要約・実行 = `sonnet`。`fable` は指定しない。`fork` 種別は親モデルを継承し `model` 引数を無視するため使わない。
  - 後ろ盾として PreToolUse hook (`.claude/settings.json` の `hooks.PreToolUse` / `.claude/scripts/subagent-model.ts`) が、`model` 未指定の Agent 呼び出し (frontmatter に `model:` を持つ種別と `fork` を除く) に `opus` を補う。hook は subagent 内の Agent 呼び出しにも発火するため、`/code-review` が内部で起動する finder / verifier や指定漏れもこれで opus に落ちる。hook は安全網であり、明示する義務を免除しない。
  - 残余: `/code-review` のオーケストレータ本体は Skill ツールが直接起動するため Agent の hook を通らず、メインのモデル (Fable) を継承する。組み込み skill を使う以上の構造的な残りとして受け入れる (2026-08-23 時点の実測で全消費の約 4%)。
- MUST: ファイル変更を伴う実装作業は、メインループが直接行わず implementer subagent へ委譲する。
- この委譲 MUST はメインセッション (メインループ) にのみ適用する。本ルールは subagent のコンテキストにも配られるが、subagent として動いている場合 (implementer 自身を含む) は再委譲せず、与えられた作業を直接行う。implementer が Agent 系ツールを持たないのはこの再帰を機械的に防ぐためであり、委譲できないことは異常ではない。
- MUST: 委譲時は工程 3 の自己完結した計画を渡す。変更内容の調査・確定 (読み取り) は工程 2 のとおり research-worker へ委譲してメインループが要点を受け取り、結果を計画に書き下す。implementer に調査から任せない。
- MUST: 既存挙動の変更を伴う計画は、委譲前に対象ファイルへ紐づく既存テストの期待値と変更内容を突合する。矛盾がある場合は、既存テストの扱い (更新可否・更新内容) を計画に明記してから委譲する。怠ると implementer は計画外の判断を禁じられているため機械的に差し戻すしかなく、往復コストだけが残る。
- MUST: implementer の完了報告後、メインループは次の 2 段でレビューする。レビュー対象の diff は、implementer の変更が乗った作業ツリーと委譲前の基点との差分 (未コミットなら HEAD との diff、コミット済みならベースブランチとの diff) とする。
  1. 計画との突合: メインループ自身が diff を読み、計画項目の実装漏れ・計画外の変更が無いかを照合する。implementer が報告した検証コマンドの実行結果もここで確認する。
  2. `/code-review` の実行: diff を対象に code-review skill を実行する。既定は medium。セキュリティ・認証・並行性・データ損失の可能性に触れる diff、または変更が複数モジュールへ広がる diff は high に上げる。「触れる」の判定は変更行の位置で行い、変更行が認証・権限判定・並行制御 (ロック・タイマー・並列 I/O)・削除や上書きの実行を含む関数の中にあれば該当とみなす。そうした処理を持つファイルでも、別の関数だけを変える diff は該当しない。同一関数内でも、副作用呼び出しの条件・引数・順序に触れない diff (出力整形・ログ追加・副作用の前後へのフラグ代入等) は該当しない。level を誤って低く走らせたと後で気づいた場合は、得られた指摘の裁定はそのまま使い、次の再レビューから正しい level で回す (初回をやり直さない)。`--fix` は使わない。レビュー対象は cwd に依存させず、`/code-review` に対象を明示して渡す (skill は current diff / PR 番号 / ブランチ / パスを対象に取る)。未コミットなら隔離 worktree のパス (作業ツリーと HEAD = 委譲前基点との diff)、途中でコミットした場合はブランチまたは基点コミットを指定する。
     指摘の裁定はメインループが行い、修正が必要なら implementer へ再委譲する。再委譲で得た修正 diff にも同じ 2 段レビューを適用する。その際の diff 基点は初回の委譲前基点に固定する (修正分だけでなく累積 diff を見る)。打ち切りは指摘ごとに数え、1 つの指摘がその指摘に対する再委譲 2 回で解消しなければ反復を打ち切り、ユーザへ判断を仰ぐ。打ち切り報告には、残存指摘・試行回数・作業ツリーの状態と、取りうる選択肢 (計画を書き換えて再承認、明示承認を得ての追加再委譲、ユーザの明示指示によるメインループの直接修正、変更の撤回) を含め、推奨を添えてよい。ユーザ判断を経て計画を改めた場合、再委譲カウントは仕切り直す。ドキュメントのみの diff では正当性レビューの効果が薄いため、(1) の突合のみでよい。
- MUST: `/code-review` の指摘は、メインループの裁定 (採用 / 不採用とその理由) を添えて全件ユーザへ開示する。不採用にした指摘を省かない。指摘が 0 件だった場合もその事実を報告する。裁定した修正の再委譲は開示と並行して進めてよいが、開示を省いて修正だけを報告しない。 承認済み計画の範囲内で行う指摘への修正再委譲には追加の承認は要らない。計画自体を書き換える場合 (設計変更・対象ファイルの追加等) は再承認を取ってから再委譲する。
- 例外: 次のいずれかに該当する作業は委譲オーバーヘッドが勝るため、メインループが直接行ってよく、2 段レビューも不要。判定に迷う場合は例外を適用せず通常フロー (委譲 + 2 段レビュー) に倒す。
  - 単一ファイルかつ変更 5 行以内の修正 (typo・設定値 1 箇所等) で、挙動の意味変更を伴わないもの
  - 意味変更を伴わない同一パターンの機械的置換 (件数・行数を問わない)
  - 散文の文書 (ルール・CLAUDE.md・skill 本文・agent 定義・README 等) の執筆・改稿。自己完結した計画に変更内容を書き下すことが本文を書くことと等価になり、委譲しても転記の往復しか残らないため。判定は変更対象のファイル種別で行う。テスト・型チェックで検証する成果物 (ソース・設定ファイル) を含む変更は例外に含めない。散文中のコマンド例・インラインコード・コードフェンスは散文の一部として扱う。文書のみでも計画と本文が分離できるもの (既定値の一括差し替え等) は例外に含めない。
- 例外に該当してメインループが直接行う場合も、工程 1〜4 (隔離・調査・計画・承認) と 7〜8 (コミット / PR・片付け) は踏む。計画は承認用 (目的・変更内容・検証・コミット方針) で足り、会話文脈に依存しない自己完結性は委譲時の要件。コミット前に diff をユーザへ提示する。これは報告であり承認待ちにはしない (計画を変える場合のみ再承認)。
- メインループ側の委譲義務 (作業の外出し・implementer への実装委譲) の強制力は instruction レベルであり機械的な enforcement は無い。メインループはツールを打つ前に、この分担に反していないか確認する。機械的に担保されているのは subagent のモデル (PreToolUse hook による `opus` 補完) だけで、それも明示義務の代わりにはならない。
