# 手を動かす領域 (インフラ・CI/CD)

ユーザが自分で扱える状態を保ちたい領域では、エージェントが先に設定やコマンドを書かず、ユーザの初手を受けてレビューに回るルール。目的はユーザの理解の維持であり、作業効率ではない。理由: この領域の誤りはテストで落ちず、請求・障害・権限の穴として遅れて現れる。承認する側にモデルが無いと、エージェントが書いた設定の妥当性を判定できない。

本ルールは dev-workflow ルールの工程 2〜3 の前段として働く。ユーザの下書きが存在した時点から通常の工程に戻る。

## 適用範囲

- AWS・GCP・Cloudflare のリソース操作 (コンソール・CLI・API) と、その IaC (Terraform / OpenTofu の HCL、wrangler の設定等)。
- GitHub Actions の workflow ファイル (`.github/workflows/`)、composite action、reusable workflow。
- `gh` による Actions・リポジトリ設定・権限の操作。
- 対象外: それらの上で動くアプリケーションコード。既存 workflow や既存 IaC の読み取りだけの調査。`gh pr` / `gh issue` 等の PR・issue 操作 (dev-workflow の工程 7 で pr-publisher が行うものを含む)。

## 初手の制約

- MUST: 範囲内の設定・コマンドをエージェントが最初に書かない。順序は次のとおり。
  1. 意図: ユーザが「何を・どの権限で・何をトリガに (または何を境界に)」を散文で書く。無ければエージェントがこの 3 点を問う。
  2. 下書き: ユーザが最初の下書きを書く、または最初のコマンドを打つ。
  3. レビュー: エージェントは下書きと出力に対して、穴の指摘とドキュメントの引き当て (research ルール) を行う。書き直して返さず、指摘で返す。
- 下書きの分担: 定型部分 (YAML の骨格・provider ブロック・`terraform` ブロック等) は、ユーザの求めに応じてエージェントが打ってよい。次の行はユーザが書く行とし、エージェントは空欄またはコメントで位置だけ示す。
  - GHA の `permissions:`、secrets の参照、OIDC の trust 設定
  - IAM の policy・role・trust policy、service account の権限、Cloudflare token の scope
  - DNS レコードの値、network (VPC・SG・zero trust 等) の定義
- MUST: 下書きが無い状態で implementer に範囲内のファイルを書かせない。下書きが存在した時点から dev-workflow の工程 2 以降 (調査・計画・承認・委譲・レビュー) を通常どおり適用する。

## 失敗時

- MUST: 範囲内の実行 (apply・workflow の実行・`gh` の操作等) が失敗したら、エージェントは原因を先に言わない。ユーザがログを読んで仮説を 1 行書くのを待ち、その後に補足・訂正する。
- ログの取得手段 (`gh run view --log` 等) の案内はしてよい。読むのはユーザ。

## 脱出路

- ユーザが「代行」と書いたら、その作業に限り本ルールを外して dev-workflow の通常フローで進める。理由: 急ぎの作業で毎回止まると、ルールごと外されて目的が消える。
- 「代行」の効力はその 1 作業 (1 つの依頼) に限り、会話全体には及ばない。

## 原則との関係

CLAUDE.md の「作業内容を提示し承認を得る」は変わらない。本ルールが変えるのは提示の中身で、範囲内では「エージェントが書いた設定」ではなく「ユーザが書く 3 点と、エージェントが打つ定型部分の切り分け」を提示する。
