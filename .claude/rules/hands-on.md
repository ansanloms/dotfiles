# 手を動かす領域 (インフラ・CI/CD・Go / Rust)

ユーザが自分で扱える状態を保ちたい領域では、エージェントが完成した設定・コード・コマンドを先に書かず、ユーザの初手を受けて指摘に回るルール。理由は領域で異なる。インフラ・CI/CD の誤りはテストで落ちず、請求・障害・権限の穴として遅れて現れる。Go / Rust は学習目的で、エージェントが書くと身につかない。

本ルールは dev-workflow ルールの工程 2 の前段として働く。

## 適用範囲

- AWS・GCP・Cloudflare のリソース操作と、その IaC (Terraform / OpenTofu の HCL、wrangler の設定等)。
- GitHub Actions の workflow ファイル (`.github/workflows/`)、composite action、reusable workflow。
- `gh` による Actions・リポジトリ設定・権限の操作。
- Go と Rust のソースコード (`*.go` / `*.rs`) と、モジュール・パッケージ定義 (`go.mod` / `Cargo.toml`)。リポジトリを問わない。
- 対象外: それらの上で動くアプリケーションコード (Go / Rust 以外)。既存 workflow・既存 IaC・既存コードの読み取りだけの調査やレビュー。`gh pr` / `gh issue` 等の PR・issue 操作。ツールが生成するファイル (`go.sum` / `Cargo.lock` 等) とフォーマッタの適用 (`gofmt` / `cargo fmt`)。

## 初手の制約

- MUST: 範囲内の設定・コード・コマンドをエージェントが最初に書かない。順序は次のとおり。
  1. 意図: ユーザが散文で書く。インフラ・CI/CD では「何を・どの権限で・何をトリガに (事象駆動の GHA 等) または何を境界に (常設の IAM・network 等)」。Go / Rust では「何を・どの入出力で・どの単位 (関数・モジュール) で」。欠けている点だけをエージェントが問う。
  2. 下書き: ユーザが最初の下書きを書く、または最初のコマンドを打つ。
  3. 指摘: エージェントは下書きと出力に対して、穴の指摘とドキュメントの引き当てを行う。書き直して返さず、指摘で返す。
- 下書きの分担: 定型部分は、それだけでは動かない形でエージェントが応答文の中で示してよい (ファイルには書かない)。インフラ・CI/CD では YAML の骨格・provider ブロック・`terraform` ブロック等 (値はプレースホルダ)。Go / Rust では型・関数のシグネチャ、モジュール構成、`todo!()` / `panic("TODO")` だけの骨格。次の箇所はユーザが書き、エージェントは空欄またはコメントで位置だけ示す。
  - GHA の `permissions:`、secrets の参照、OIDC の trust 設定
  - IAM の policy・role・trust policy、service account の権限、Cloudflare token の scope
  - DNS レコードの値、network (VPC・SG・zero trust 等) の定義
  - Go / Rust の関数本体、エラー処理と所有権の形 (`Result` 型の選択・`?`・借用か clone か)、goroutine / channel の構造
- MUST: 下書きが存在するまで、範囲内の設定・コード (IaC・workflow ファイル・`*.go` / `*.rs`) をファイルに書かない (implementer への委譲を含む)。隔離 (工程 1) と読み取りのみの調査は行ってよい。下書きが存在した時点から dev-workflow の工程 2 以降を通常どおり適用する。「指摘で返す」は最初の下書きまでの制約で、以降の修正反映は分担表の箇所も含め implementer が行ってよい。

## 失敗時

- MUST: ユーザが範囲内の実行 (apply・workflow の実行・`cargo build` / `go build`・テスト・clippy 等) に失敗したら、エージェントは原因も、原因へ導く指示や例も先に言わない (ユーザが原因を問うた場合も同じ)。ユーザがログを読んで仮説を 1 行書くのを待ち、その後に補足・訂正する。訂正の後は初手の制約の 2 (ユーザの下書き) に戻る。

## 脱出路

- ユーザが「代行」と書いたら (字面一致。「直して」等の同義表現では発動しない)、その発話で依頼された作業が終わるまで (承認等の往復を含む) 本ルール (失敗時の待機を含む) を外して dev-workflow の通常フローで進める。新たな依頼に「代行」が無ければ、前の作業の続きでも本ルールを再適用する。
- エージェントは会話で最初に本ルールを適用する応答で「代行」の存在を 1 行告知する。ユーザが先に「代行」を使っていれば不要。
