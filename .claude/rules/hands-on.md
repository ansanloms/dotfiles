# 手を動かす領域 (インフラ・CI/CD)

ユーザが自分で扱える状態を保ちたい領域では、エージェントが完成した設定やコマンドを先に書かず、ユーザの初手を受けて指摘に回るルール。理由: この領域の誤りはテストで落ちず、請求・障害・権限の穴として遅れて現れる。

本ルールは dev-workflow ルールの工程 2 の前段として働く。

## 適用範囲

- AWS・GCP・Cloudflare のリソース操作と、その IaC (Terraform / OpenTofu の HCL、wrangler の設定等)。
- GitHub Actions の workflow ファイル (`.github/workflows/`)、composite action、reusable workflow。
- `gh` による Actions・リポジトリ設定・権限の操作。
- 対象外: それらの上で動くアプリケーションコード。既存 workflow や既存 IaC の読み取りだけの調査。`gh pr` / `gh issue` 等の PR・issue 操作。

## 初手の制約

- MUST: 範囲内の設定・コマンドをエージェントが最初に書かない。順序は次のとおり。
  1. 意図: ユーザが「何を・どの権限で・何をトリガに (事象駆動の GHA 等) または何を境界に (常設の IAM・network 等)」を散文で書く。欠けている点だけをエージェントが問う。
  2. 下書き: ユーザが最初の下書きを書く、または最初のコマンドを打つ。
  3. 指摘: エージェントは下書きと出力に対して、穴の指摘とドキュメントの引き当てを行う。書き直して返さず、指摘で返す。
- 下書きの分担: 定型部分 (YAML の骨格・provider ブロック・`terraform` ブロック等) は、それだけでは動かない形 (値はプレースホルダ) でエージェントが応答文の中で示してよい (ファイルには書かない)。次の箇所はユーザが書き、エージェントは空欄またはコメントで位置だけ示す。
  - GHA の `permissions:`、secrets の参照、OIDC の trust 設定
  - IAM の policy・role・trust policy、service account の権限、Cloudflare token の scope
  - DNS レコードの値、network (VPC・SG・zero trust 等) の定義
- MUST: 下書きが存在するまで、範囲内の設定 (IaC・workflow ファイル) をファイルに書かない (implementer への委譲を含む)。隔離 (工程 1) と読み取りのみの調査は行ってよい。下書きが存在した時点から dev-workflow の工程 2 以降を通常どおり適用する。「指摘で返す」は最初の下書きまでの制約で、以降の修正反映は分担表の箇所も含め implementer が行ってよい。

## 失敗時

- MUST: ユーザが範囲内の実行 (apply・workflow の実行等) に失敗したら、エージェントは原因も、原因へ導く指示や例も先に言わない (ユーザが原因を問うた場合も同じ)。ユーザがログを読んで仮説を 1 行書くのを待ち、その後に補足・訂正する。訂正の後は初手の制約の 2 (ユーザの下書き) に戻る。

## 脱出路

- ユーザが「代行」と書いたら (字面一致。「直して」等の同義表現では発動しない)、その発話で依頼された作業が終わるまで (承認等の往復を含む) 本ルール (失敗時の待機を含む) を外して dev-workflow の通常フローで進める。新たな依頼に「代行」が無ければ、前の作業の続きでも本ルールを再適用する。
- エージェントは会話で最初に本ルールを適用する応答で「代行」の存在を 1 行告知する。ユーザが先に「代行」を使っていれば不要。
