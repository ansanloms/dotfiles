# 技術調査 (ライブラリドキュメント)

ライブラリ・フレームワーク・SDK・API・CLI ツール・クラウドサービスの仕様や使い方を調べる場面で、学習データに頼らず現行ドキュメントで裏取りするためのルール。取得の具体手順 (Context7 CLI の実行方法・ライブラリ ID の選択基準・クエリの書き方・エラー処理) は `find-docs` skill に委譲し、本ルールは「いつ使うか」「取得結果が部分的だった場合の回答の扱い」「subagent へ委譲するときの扱い」を定める。

## 原則

- MUST: ライブラリ・フレームワーク・SDK・API・CLI ツール・クラウドサービスの API 構文・設定方法・バージョン移行・セットアップ手順・CLI の使用方法を調べるときは、`find-docs` skill を使う。ユーザの質問に回答する場面と、実装計画を立てるための調査の場面の両方に適用する。
- MUST: 答えを知っていると思っても、学習データだけで回答・計画しない。WebSearch・WebFetch を ctx7 の代替にしない (メインループ・subagent を問わない)。
  - 取得できなかった場合は取得不可の事実を伝え、該当箇所の回答・計画を保留する (詳細は skill の「エラー処理」節)。
  - 取得結果が部分的 (オプション名・型は取れたがコード例が無い等) で、それらを組み合わせてコード例や手順を自分で構成する場合は、ドキュメント由来の事実と自分が構成した部分を回答内で区別して明示する。
  - 保留と構成の境界は、問われた事実そのもの (オプション名・引数・設定値・挙動等) が取得できたかで引く。取得済みと認定するのは、問われたシンボル (型・関数・オプション) 自体の本文または要約にその事実が書かれている場合に限る。別シンボルの記述からの類推は構成部分として区別表示する。
- 適用境界は `find-docs` skill の description に従う。コードベース内のシンボル・参照の調査 (lsp ルール) や grep による探索も本ルールの対象外。
  - 適用の判定単位はタスクの種別ではなく、いま確定しようとしている個別の事実がライブラリ仕様 (API の引数・戻り値・設定値・挙動) かどうか。対象外のタスクの途中でライブラリ仕様に触れる必要が出たときは、取得するか、その仕様に依存しない言い方 (観測した事実・既存コードの形) に書き換えて取得を避けるかを選んでよい。
  - 取得が必須になるのは、仕様を断定して回答や計画の根拠にする場合に限る。断定かどうかは語調ではなく依存関係で決める。回答や計画の正否がその仕様の真偽に依存する書き方なら、「候補」「可能性」と弱めても断定として扱う。
- 同一の論点 (ライブラリと質問の組) について一度取得した結果は、同じ会話内で再利用してよい。取得済みの結果で足りるのに再取得しない。

## subagent へ委譲するときの扱い

- `research-worker` subagent は `Skill` ツールを持たないため、`find-docs` を直接起動できない。ライブラリ仕様の調査を `research-worker` へ委譲する場合、委譲プロンプトには次を含める。
  - `~/.claude/skills/find-docs/SKILL.md` を Read し、そこに書かれた手順 (library → docs)・選択基準・バージョン指定・実行上限・エラー処理に従って実行すること。
  - ライブラリ名と、英語で書いた具体的な質問文 (クエリ)。skill の手順は library と docs の 2 段で、クエリは段ごとに分けてよい (docs 用は API 名等で絞る)。分けない場合は 1 本を両段に使う。
  - 返却物: 取得したドキュメントの要点、各要点の Source URL、選択したライブラリ ID とその理由 1 行、実行したコマンド回数。取得結果にバージョン・unstable・pre-release 由来の注記があればそれも含める (無ければ「注記なし」と返させる)。取得結果に無い内容を補わせない (コード例が無ければ「無い」と返させる)。
  - 取得できなかった場合は、取得不可の事実とその理由 (エラーメッセージ) だけを返すこと。学習データで埋めない。
- メインループは `find-docs` を自分で起動せず、実行を `research-worker` へ委譲する (dev-workflow ルールの工程 2。`model` 等の起動パラメータも同ルールに従う)。理由:「ID は既知だから docs だけ打つ」という省略は skill に存在せず、学習データ由来の ID を持ち込む抜け穴になる。同じ会話で取得済みの結果の再利用 (原則の最終項) はこの限りでなく、再取得自体が不要。
- `implementer` へ渡す実装計画にライブラリ仕様が関わる場合、その仕様は委譲前に確定して計画に書き下す。implementer に取得させない。
