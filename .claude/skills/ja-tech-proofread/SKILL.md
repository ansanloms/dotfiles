# 日本語技術文章の推敲

日本語の技術文書 (markdown) を読み、機械判定できない層の問題を直す。対象は段落と論証の構成、箇条書き項目の書き方、文の一義性、語彙、事実と意見の区別。本文だけから決まる修正は構成の変更も含めてファイルへ適用し、著者の判断が要る箇所はその場で確認してから適用する。文書を書き上げた著者、または著者に代わって文書を確認するエージェントが、公開・コミット前の確認に使う。

## 分担

- 表記と文法の機械判定は textlint (`textlint-rule-preset-ansanloms`) が担う。lint 設定は `scripts/.textlintrc.js` (preset をそのまま有効化) で、この skill が rule を上書きすることは無い。textlint が出した指摘は機械層として報告に転記し、この skill は再判定しない。
- preset が無効化した rule のうち、この skill が意味の側から引き取るのは 2 つ。
  - `ja-no-weak-phrase` は S2、`no-doubled-joshi` は S3 で扱う。
  - 理由: この 2 つは機械判定では誤検出が出るため preset が無効化している。
- S 群の他の規範は、有効な rule と重ならない範囲を扱う。
- それ以外に lint が拾わない表記・文法の現象 (括弧の幅、カタカナ長音、外来語の表記等) があっても、この skill は表記・文法を判定しない。rule の有効・無効の一覧は preset の README を正とする。
- 文体 (常体か敬体か) は扱わない。文体は lint 設定が決める。

## 受け取り

Skill ツールの `args` を次の文法で解釈する。

```
<mode> <path...>
```

- `mode`: `fix` または `lint`。省略時は `fix`。
  - `fix`: 機械層を `--fix` で直し、意味層の修正を完結させる。本文だけから決まる修正 (構成の変更を含む) はファイルへ直接適用する。著者の判断が要るもの (要判断) はその場でユーザに確認してから適用する。
  - `lint`: ファイルを変更せず、すべての指摘を一覧で返す。
- `path...`: 対象ファイルの絶対パス。省略時は会話で指定された対象 (ファイルパスまたは貼り付けられた本文) を使う。
  - 複数対象: 複数渡された場合は、機械層の実行・推敲・報告をファイルごとに分けて行い、会話にはファイルごとに 1 行ずつ返す。
  - 範囲指定: 見出し名や行範囲の指定があればその範囲だけを見る。範囲指定があっても機械層 (textlint と deno fmt) はファイル全体に効き、範囲外の自動修正も集計の M に含める。
  - 貼り付け本文: 貼り付け本文が対象の場合は、報告ファイルと同じ出力ディレクトリ (「報告書式」節。1 回の実行で 1 回だけ確保する) に `input-<YYYYMMDD-HHMMSS>.md` として書き出し、以後はそのファイルを対象として扱う。報告の書き方は「報告書式」節の「貼り付け本文との差分」に従う。報告ファイルは同じタイムスタンプで `proofread-input-<YYYYMMDD-HHMMSS>.md` とする。

description による自動発動で `args` が無い場合は、mode を `fix`、path を会話文脈から取る。

### スクリプトの場所

機械層は `scripts/` の textlint で実行する。実行のたびに次のループを 1 回だけ走らせて絶対パスを解決し、以後は結果をリテラルで書き下す。理由: エージェントのシェルは呼び出しごとに cwd と変数を失う。

```sh
for d in "$(git rev-parse --show-toplevel 2>/dev/null)/ja-tech-proofread" "$PWD/.claude/skills/ja-tech-proofread" "$HOME/.claude/skills/ja-tech-proofread"; do
  if [ -d "$d/scripts" ]; then echo "$d/scripts"; break; fi
done
```

候補の順は、作業中のリポジトリ内 (`git rev-parse --show-toplevel` 基準、source of truth)、配布先、ユーザ共通。最初に見つかった 1 件を使う。理由: 配布先の複製はインストール時点のスナップショットで、開発中のリポジトリでは古くなり得る。0 件なら推測せず、機械層を「実行不可 (scripts 未検出)」として手順 1 へ進む。内部動作は `scripts/README.md` を参照。

## 手順

0. 機械層。対象が複数なら path ごとに行う。
   - 準備: `<scripts>/deno.json` の `imports` から preset の alias 先 URL を控え、報告ヘッダに使う。
   - 出力: 出力 O・O1・O2 はコマンドの標準出力と標準エラーを合わせたもの (`2>&1`) とする。実行環境の警告行 (Node の DeprecationWarning 等) も含めてそのまま扱う。色などの ANSI 制御コードは除く。
   - 取得形: 取得はパイプを使わず `<コマンド> > <一時ファイル> 2>&1; rc=$?` の形で行い、終了コードを先に確保してから一時ファイルの ANSI 制御コードを除く。理由: パイプに流すと終了コードを失う。
   - コマンドの記録: 実行したコマンドは実行順にすべて (`lint` は 2 本、`fix` は 3 本) 報告ヘッダに列挙する。
   - `lint` モード: (a) `deno task -q --cwd "<scripts>" textlint <path>` を実行して出力 O と終了コードを得て、(b) `deno task -q --cwd "<scripts>" fmt:check <path>` を実行して整形差分の有無を得る。自動修正の件数 M は 0。
   - `fix` モード:
     - (a) `--fix` 付きの textlint を実行して出力 O1 から M を取る (`✔ Fixed N problem` の行があれば N、無ければ 0。実物の例: `✔ Fixed 1 problem`。取得コマンド `deno task -q --cwd "<scripts>" textlint --fix <probe>`、取得日 2026-08-31)。O1 に該当行が無くても O1 はそのまま報告に貼り、末尾に「自動修正 0 件」と書く。
     - (b) 対象のハッシュ (`md5sum`) を取ってから `deno task -q --cwd "<scripts>" fmt <path>` を実行し、直後にもう 1 度ハッシュを取って整形の有無を決める。
     - (c) `deno task -q --cwd "<scripts>" textlint <path>` (`--fix` 無し) を実行して出力 O2 を得る。
   - O1 の扱い: O1 は実行可否の判定にだけ使い、`No rules found` を含めば実行不可として (b) (c) は行わない。指摘件数の分類は O または O2 (それぞれ `lint`、`fix`) にだけ当てる。解釈・要約・再判定はしない。
   - 実行不可: 出力に `No rules found` を含む、または終了コードが 2 以上 (対象が見つからない場合の `Not found target files` 等)。報告には「実行不可 (理由)」と書き、以降の手順は続行する。
   - 指摘あり: 上記以外で終了コードが 1。残り件数 K は `✖ N problem` または `✖ N problems` の行の N (1 件のときは単数形で出る)。
   - 0 件:
     - 終了コードが 0。warning や info の行だけが出ていても 0 件とする。K は 0。
     - 報告には出力をそのまま貼った上で「指摘 0 件 (終了コード 0)」と書く。
   - 整形: `fmt`・`fmt:check` は skill 自身の設定 (`scripts/deno.json`、`proseWrap: preserve`) で動き、対象が属するプロジェクトの fmt 設定と除外は見ない。`fmt` が 0 以外、`fmt:check` が 0 と 1 以外の終了コードで終わった場合 (対象が見つからない等) は、整形は実行不可とし「整形: 実行不可 (理由)」と書き、textlint の結果はそのまま扱う。
   - 集計:
     - 集計の機械層は「自動修正 M 件、整形あり、残り K 件」または「自動修正 M 件、整形なし、残り K 件」と書く。
     - 整形の有無は `fix` モードでは (b) の前後のハッシュが異なれば「整形あり」とする。理由: `deno fmt` は変更の有無を出力しない。`lint` モードでは `fmt:check` の終了コードが 1 なら「整形あり」、0 なら「整形なし」。
     - 実行不可のときは「機械層 (実行不可)」と書く。整形の語はこの 2 値だけを使い、「整形差分あり」等の別表現は使わない。
     - 機械層の実行はこの手順 0 の 1 回だけで、報告の値はこの時点のもの。手順 4 の適用後に textlint を再実行してもよいが、その結果は報告に載せず、新たな指摘が出た場合は該当する適用を戻す。
1. 節の分割と種別判定。
   - 見出し (`#` で始まる行。コードフェンス内の行は除く) ごとに節を切る。見出しが無い文書は全体を 1 節とする。
   - 各節について、見出し行・表・コードフェンス・frontmatter を除いた非空行のうち、箇条書き行 (`-`、`*`、`1.` 等で始まる行と、そのインデント継続行) が過半なら「項目」、そうでなければ「散文」とする。判定対象の非空行が 0 の節は「散文」とする。
   - 見出し行そのものが箇所になる指摘 (D3 等) の節種別は、その見出しが開く節の種別とする。
2. pass 1 (構成)。規範の適用 (手順 2〜4) では、表・コードフェンス・frontmatter の中身を対象から除く。
   - D 規範を文書全体に当てる。
   - P 規範は散文の節と、項目の節に並置された独立の散文段落に当てる。
   - L 規範は層内で範囲が異なる。
     - L3 は全節に当てる。理由: S4 が括弧の割り込みを L3 に委ねる。
     - L4・L5 は項目の節に当て、その節に並置された散文段落も含める。
     - L1・L2・L6・L7 は項目の節の箇条書き行にだけ当てる。
   - R 規範を全節に当てる。
3. pass 2 (文と語彙)。S 規範と H 規範を全節に当てる。
4. 適用。`fix` モードでは、pass 1・pass 2 の指摘を 2 つに分けて処理する。
   - 修正が本文だけから決まるもの (構成の変更を含む) はファイルへ適用する。
   - 著者しか持たない情報が要るもの (確認の有無、根拠、別々の語が同一物を指すか等) は「要判断」とする。その場でユーザに選択肢 (2 つまで) を提示して確認し、回答に従って適用する。回答が「直さない」ならその旨を報告の「ユーザ判断」に記録する。
   - 確認できる相手がいない実行 (subagent 経由等、会話にユーザがいない場合) では、要判断を適用せず「ユーザ判断待ち」として報告に残す。
   - `lint` モードなら何も適用しない。
5. 報告。「報告書式」に従って組み立てる。箇所の行番号と件数の基準は「報告書式」節の規則に従う。

pass 1 を pass 2 より先に回す。理由: 構成の修正 (段落の分割・項目の統合) で文そのものが消えるため、文の修正を先に出すと無駄になる。

## 規範

各規範は ID で参照する。「適用」列は当てる節種別、「根拠」列は規範の根拠を示し、公開基準に由来するものは出典を書く。出典の詳細は [references/sources.md](references/sources.md) にある。`fix` モードでの適用は規範の群ではなく、修正が本文だけから決まるかで分ける (手順 4)。

| L1 | 1 項目 1 規範。強度 (MUST・推奨・禁止・任意) を語で明示する。強度の無い項目は事実の記述として読める形にする                                                                                                                                            | 項目 (箇条書き行)               | 走査して読む前提                                    |

### S: 文 (個別の例外は規範文に従う)

## 判断の指針

- 指摘と修正は必ず規範 ID に結び付ける。ID に対応しない指摘は出さない。
- 確信が持てる場合だけ指摘する。規範の文言に当てはまるかどうかで迷う箇所は指摘しない。
- 修正は著者の意図を変えない範囲で行う。意図が読めない場合は要判断とし、手順 4 に従ってユーザに確認する。
- 規範文の除外条件 (S5 の「文脈から自明」等) が先に効く。同じ句に要判断 (H2 等) が掛かる修正は、要判断の確認とまとめて 1 回でユーザに聞き、回答に従って両方を処理する。
- 同じ規範の同じ問題 (規範違反の型が同じもの) が繰り返すときは、`lint` モードの「指摘 (未適用)」表では最初の 3 件を箇所付きで挙げ、残りは件数だけ「同 ID の残り N 件」として書く。
  - この集約は「指摘 (未適用)」表にだけ掛かる (fix モードの「ユーザ判断」には掛けず、確認は問題の型ごとにまとめて 1 回でよい)。
  - `fix` モードではすべてに適用し、「適用した修正」表には適用したすべてを箇所付きで載せる。
  - 閾値未満 (3 件以下) は 1 件 1 行で書く。
- 用語の不統一は、項目の節 (箇条書き行) で見つかれば L7、散文の節なら S7 で扱う。S7 はそれに加えて初出定義の欠落と曖昧語への後退を扱う。
- 機械層 (lint) が既に出した指摘は pass 1・pass 2 で再掲しない。
- 規範同士が衝突する場合は、文書レベルの規範 (D) を優先し、その旨を「問題」欄に書く。衝突の例は D4 の転記禁止と D1 の冒頭説明。
- 1 つの修正が別の指摘を解消する場合 (節の削除で節順序の問題が消える等) も、指摘は別々の行に立て、修正案欄に依存を書く。ここで省略しないのは依存関係のある別種の指摘で、同 ID の同型反復は前項の集約に従う。
- 報告書式の例に載っている指摘を、対象文書の指摘として流用しない。例は書式の見本で、対象の判定は毎回行う。

## 報告書式

報告はファイルに書く。

- 出力先: 呼び出し側が出力先を指定していればそこが正本で、指定はディレクトリとして解釈する。指定が無ければ非汚染領域 (`$CLAUDE_JOB_DIR/tmp` があればそこ、無ければ `mktemp -d` の結果) に書く。
- ディレクトリ確保とタイムスタンプ: 出力ディレクトリの確保は 1 回の実行につき 1 回だけ行い、一時入力ファイルと報告の両方に使う。タイムスタンプ `<YYYYMMDD-HHMMSS>` は実行開始時に 1 回だけ取り、以後リテラルで使う。
- 報告名の規則: 報告名は `proofread-<対象の basename (拡張子なし)>-<YYYYMMDD-HHMMSS>.md`。貼り付け本文は例外で `proofread-input-<YYYYMMDD-HHMMSS>.md`。同じ実行で basename が重複する対象があれば、重複するものは `proofread-<親ディレクトリ名>-<basename>-<YYYYMMDD-HHMMSS>.md` とする。
- 会話への返答: 会話にはファイルのパスと集計 1 行だけを返す。

会話への返答は次の 2 行の形にする。

```
/home/user/.claude/jobs/xxxx/tmp/proofread-nvim-rule-20260831-235723.md
集計: 機械層 (自動修正 2 件、整形なし、残り 1 件)、適用 10 件、要判断 1 件
```

整形と提示手段 (エディタで開く等) は呼び出し側が決める。

### lint モードとの差分

- 「## 機械層」は「### 実行」と「### 整形」の 2 ブロックだけ。「### 実行」は textlint 1 回の出力と分類行、「### 整形」は fmt:check の出力と「整形あり」または「整形なし」を置く。「1 回目 (--fix)」「2 回目」は置かない。
- ヘッダの「機械層 (実行順)」は textlint と fmt:check の 2 本。
- 「## 適用した修正」節を置かず、集計から「適用」を落として「集計: 機械層 (自動修正 0 件、整形なし、残り K 件)、指摘 U 件 (整形があれば「整形あり」)」とする。
- 適用群 (L3〜L5・S・H・R) の指摘も「指摘 (未適用)」表に載せる。
- 「指摘 (未適用)」表の列は箇所/節種別/ID/問題/修正案とする。
- 「層別の件数」の「適用」は常に 0 件で、項目は残す。
- その他は例と同じ。

### 貼り付け本文との差分

- ヘッダの対象は「- 対象: 貼り付け本文 (一時ファイル <絶対パス>)」。タイトルの basename は一時ファイルの basename。
- 報告名は `proofread-input-<YYYYMMDD-HHMMSS>.md` (一時入力と同じタイムスタンプ)。
- 末尾に「## 修正後の全文」を置き、修正後の一時ファイルの内容を ```markdown のコードフェンスで囲んで載せる (fix モードのみ)。

### 規則

- 例と規則が食い違えば例を正とする。
- 箇所は行番号と冒頭の引用で示す。
  - 行番号と「変更前」「箇所」の引用は手順 0 完了後・手順 4 適用前のファイルを基準にし、件数・文字数・文数の計測も同じ基準にする。
  - 同じ行から複数件出る場合は該当する文の冒頭を引用して区別する。
  - 複数行にまたがる指摘は行範囲、該当行の併記、または「節順序 (L13 と L21)」のような位置の名前で示す。
- 「節種別」列は箇所が属する節の種別を書く。項目の節に並置された散文段落は「項目 (並置された散文段落)」と書く。節をまたぐ指摘は「項目・散文」のように併記する。
- 修正案が 1 行に収まらない構成の変更は、表には要点だけ書き、表の直後に補足を書いてよい。
- `fix` モードでは「指摘 (未適用)」の代わりに「ユーザ判断」節を置く。表の列は箇所/節種別/ID/問題/選択肢と回答。ユーザに確認できた行は回答と結果 (適用した/直さない) を書き、確認できる相手がいない実行では回答欄を「ユーザ判断待ち」とする。
- 「適用した修正」表で構成の変更として適用した行は、箇所欄の末尾に「(構成)」と付ける。
- 「層別の件数」には 6 層 (D・P・L・R・S・H) をすべて 1 行ずつ、各行に「適用 a 件、指摘 u 件」の両方を書く。0 件でも省略しない。
  - `fix` モードでは「指摘」の数値は要判断 (ユーザ判断表) の件数とする。
  - R2 の閾値を超えた行は指摘に上げず、件数と行番号を R の行に注記する。超えた行が無ければ「200 文字超の行なし」と書く。
- 集計の「適用 A 件」は「適用した修正」表の行数 (規範 ID ごとに 1 行)。「指摘 U 件」は `lint` モードでは「指摘 (未適用)」表の行数 (集約した行は「残り N 件」の N を加える)、`fix` モードでは「要判断 J 件」と書いて「ユーザ判断」表の行数を入れる。機械層が実行不可のときは「機械層 (実行不可)」と書き、「2 回目」と「整形」の各ブロックに「実行不可 (理由)」の 1 行だけを置く。
- 機械層の出力は標準出力と標準エラーを合わせたもの (実行環境の警告行を含む) を ``` のコードフェンスで囲んでそのまま貼る。
- 1 つの修正が別の指摘を解消する場合も、指摘は別々の行に立て、修正案欄に依存を書く。

## 持ち込まないもの

- 表記と文法の機械規則 (「分担」節の通り)。
- 文体の指定。
- 一文一行の整形。書籍原稿の版管理向けの規範であり、markdown 文書には当てない。
- 見出し内の太字、箇条書き先頭の絵文字。lint の `no-ai-emphasis-patterns` と `no-ai-list-formatting` の担当。
- 要約・翻訳・執筆の代行。
- コードやコメントのレビュー。
- 英語文書。
- 特定の原稿に固有の術語や書式。

## 呼び出し側の責務

- 対象の指定 (ファイルパスまたは本文) と、範囲の指定。
- モードの選択 (省略時は `fix`)。
- 報告ファイルの出力先の指定 (任意)。
- 提示手段 (コンソール、エディタ等) の選択。
