# review-loop

dev-workflow ルールの「レビュー」節を実行するための手順。判断 (裁定・設計変更の判定・終了の決定) はルールの基準で呼び出し側が行い、この skill は台帳・range・委譲文・遷移の型を提供する。

## 受け取り

呼び出し側から次を受け取る。Skill ツールの `args` に `key=value` を空白区切りで並べる (値に空白を含むものはシングルクォートで囲む。例: `ledger=/tmp/x/ledger.md repo=/path/wt base=main branch=feat/x load='git -C /path/wt config --get branch.feat/x.review' store='git -C /path/wt config branch.feat/x.review "$(cat {file})"'`)。`ledger` が無ければ台帳に関わる手順全体を止め、供給を求める (自前で場所を決めない)。

| 引数     | 必須 | 意味                                                                                                           |
| -------- | ---- | -------------------------------------------------------------------------------------------------------------- |
| `ledger` | 必須 | 台帳ファイルの絶対パス。空白や記号を含まないパスを渡すこと      |
| `load`   | 任意 | 標準出力に台帳を吐くコマンド。ラウンド開始時に `sh -c` で実行し、出力を `ledger` に書く                        |
| `store`  | 任意 | 台帳を永続化するコマンド。`{file}` を `ledger` のパスに置換して `sh -c` で実行。台帳を書き換えるたびに実行する |
| `repo`   | 必須 | 対象リポジトリ (隔離 worktree) の絶対パス。range の算出と implementer / runner への委譲に使う                  |
| `base`   | 必須 | 比較元ブランチ (通常 `main`)                                                                                   |
| `branch` | 必須 | 作業ブランチ名                                                                                                 |

`load` / `store` の中身 (git config か別の手段か) はこの skill は知らない。`load` が失敗 (非 0) または空なら台帳を初期化する。`store` が失敗したら、裁定の開示 (手順 5-8) だけ行い、状態を変える手順 (再委譲・手順 8・次ラウンド) を止めて呼び出し側に報告する。`ledger` ファイルを正として残し、復旧後に store をやり直してから再開する。`load` / `store` が無ければ `ledger` ファイルそのものが正本。

例 (git config を正本にする場合の供給値):

```sh
ledger=/path/to/tmp/review-ledger.md
load='git -C /path/to/worktree config --get branch.feature/x.review'
store='git -C /path/to/worktree config branch.feature/x.review "$(cat {file})"'
```

## 台帳の書式

テンプレートは `assets/` に置く。本文に写さず、そこから埋める。

| ファイル                  | 用途                                           |
| ------------------------- | ---------------------------------------------- |
| `assets/ledger.md`        | 台帳の初期形 (ヘッダ + 空の findings / rounds) |
| `assets/round.md`         | rounds 節に追記するラウンド 1 回分             |
| `assets/runner-prompt.md` | code-review-runner への委譲文                  |

- ヘッダ: `state` は `in-progress` / `done` / `cut-off (<理由>)`。`last-reviewed` は直近ラウンドでレビューした HEAD の SHA。`rounds` は実施済みラウンド数。
- findings: 1 指摘 1 行。id はブランチ内の通し番号 (`#n`)、初出は最初に記録したラウンド (`rN`)。ラウンドをまたいで同じ症状は同じ id を使い、行を増やさない。同一性は「症状」列 (同じ入力でどう壊れるか) で判定する。
- 裁定は 5 値: `採用 (未解消 n/2)` / `採用 (解消 rN)` / `採用 (設計変更・承認待ち)` / `不採用` / `ユーザ判断`。`n` はその指摘への再委譲のうち解消に至らなかった回数。裁定が変わったら同じ行を書き換える (履歴は rounds に残る)。
- 再出現した `不採用` / `ユーザ判断` は `理由 / 状態` 列末尾に `再出現 rN` を追記する。
- 場所は `ファイル 関数名` を優先 (行番号はずれる)。症状・理由に `|` を使わない。
- rounds は id の列挙だけで散文を書かない。

### 読み書き

- 初期化: `assets/ledger.md` を `ledger` にコピーし、`<branch>` / `<base>` を埋める。
- 書き換え: `ledger` を編集 → `deno fmt --ext md --prose-wrap preserve` で整形 (表の縦線は fmt が表示幅で揃える。手で揃えない) → `store` があれば実行。

  ```sh
  deno fmt --ext md --prose-wrap preserve - < "$ledger" > "$ledger.tmp" && mv -f "$ledger.tmp" "$ledger"
  if [ -n "$store" ]; then sh -c "$(printf '%s' "$store" | sed "s|{file}|$ledger|g")"; fi
  ```

## WIP コミット

- implementer への委譲文の末尾に必ず付ける: 「変更を `git add` し、`wip: implement` (初回) / `wip: review rN` (ラウンド N の修正) の固定文言でコミットする。push はしない」。
- WIP はレビュー中に implementer が行う唯一のコミット。内容をメッセージに書かせない。

## ラウンドの手順

### 0. 開始

1. `load` があれば実行して `ledger` に書く。無ければ `ledger` を読む。無ければ初期化。初期化も書き換えと同じ扱い (fmt → store)。
2. `rounds` を読み、今回を `rN` (N = rounds + 1) とする。

### 1. range と level

| round   | range                    | level              |
| ------- | ------------------------ | ------------------ |
| r1      | `<base>...<branch>`      | 計画に書いた level |
| r2 以降 | `<last-reviewed>...HEAD` | `medium` 固定      |

r1 で網羅性を取り、r2 以降は確信の高い指摘だけを増分に対して取る。r2 以降を `high` にしない (r1 が `high` でも同じ)。

計画に書く level と天井の既定:

- level は既定 `medium`。変更がセキュリティ・認証・並行制御 (ロック・タイマー・並列 I/O)・削除や上書きに関わるか、複数モジュール (パッケージ境界。無ければトップレベルディレクトリ。ルート直下のファイルはまとめて 1 モジュール) に広がる diff は `high`。迷ったら `high`。
- 天井は単一モジュールで `medium` 相当なら 3、複数モジュールか `high` 相当なら 4。計画に明示した値があればそれ。

`HEAD SHA` は `git -C "$repo" rev-parse --short HEAD`。range は用途で表記が違う: runner への委譲文と `git diff` には実行時解決形 (`<last-reviewed>...HEAD`)、台帳の rounds には解決済み SHA (r1 は `<base>...<branch> @ <HEAD SHA>`、r2 以降は `<last-reviewed>...<HEAD SHA>`) を書く。

### 2. 突合

`git -C "$repo" diff <range>` を読み、計画との差 (実装漏れ・計画外の変更) と implementer の検証結果を確認する。

### 3. runner への委譲

code-review-runner を Agent で起動する。`description` は `code-review rN` (取り直しは `code-review rN retry`)。委譲文は `assets/runner-prompt.md` を埋めて使う。項目を足さない (返却の形は runner の agent 定義が縛る)。台帳・不採用事項・検証結果・意図した設計を添えても reviewer には届かない (fork は skill 本文と target 文字列しか受け取らない)。

### 4. 返却の判別

生と判定する条件: 指摘ごとに 場所 (ファイルと行または関数)・要約・失敗シナリオ が付いて列挙されている (`medium` 以上は `file` / `line` / `summary` / `failure_scenario` の JSON 配列で返る。0 件は空配列または `(none)`)。重さ・新規 / 既知の欄は `/code-review` の返却形に無いので要求しない。判定は形式検査のみで、値の妥当性 (行番号のずれ等) は裁定側で扱う。

加工と判定する条件のいずれか: 総評の散文だけ、採用 / 不採用 / 既知等の裁定語付き。加工なら同じ委譲文で 1 回だけ取り直す。取り直しても加工なら「加工済み」と明記してユーザへ判断を仰ぐ。

### 5. 裁定

1. `assets/round.md` を rounds 節の末尾に追記する。各項目は以降の手順で埋め、最後に値の無い項目は行ごと消す。
2. 照合: 返った指摘ごとに、症状 (同じ入力でどう壊れるか) を findings の全行と突き合わせる。同じ症状の行があればその id を当て、行を増やさない。原因の説明・修正後の機構・関数の分割・改名・移動の違いでは別扱いにしない。
   - `不採用` / `ユーザ判断` に当たった: 既知。裁定しない。`known` に id を書き、`理由 / 状態` 列に `再出現 rN` を追記する。照合が誤り (症状が実は異なる) と判断したら新規として 3 へ。
   - `採用 (未解消 n/2)` に当たった: 未解消の再報告。新規にせず 5 で扱う。
   - `採用 (解消 rN)` に当たった: 再発。裁定を `採用 (未解消 n/2)` に戻し (`n` は据え置き)、`理由 / 状態` 列に `再発 rN` を追記する。5 の未解消として扱う。
3. どの行にも当たらない指摘を 採用 (`採用 (未解消 0/2)`) / 不採用 / ユーザ判断 に裁定し、findings に行を足す (id は既出の最大 id + 1。行は表の最終行の直後に挿入し、表を分割しない)。`new` に id を書く。
4. 採用した指摘ごとに、下記「設計変更の定義」の表で 修正 / 設計変更 を判定する。設計変更は `採用 (設計変更・承認待ち)` とし、`design-change` に id を書く。
5. 前ラウンドの `採用 (未解消 n/2)` について、修正が増分 diff にあり、かつ今回同じ症状の再報告が無いものを `採用 (解消 rN)` に書き換え、`resolved` に書く (`理由 / 状態` 列は修正方針のまま残す)。修正が増分 diff に無い、または同じ症状が再報告されたら解消とせず、`n` を 1 増やして `理由 / 状態` 列に突合結果を書く。
6. `verified` に implementer が報告した検証コマンドと結果を写す (再実行せず、突合と矛盾しても書き換えない。矛盾は 5 の `理由 / 状態` 列に残る)。ヘッダの `rounds` を N に、`last-reviewed` を今回の HEAD SHA にする。
7. 台帳を書き換え (fmt → store)。
8. 裁定を全件ユーザへ開示する。設計変更があれば同じターンで、id ごとに「計画の該当箇所 / before / after」を並べて承認を求める。

### 6. 設計変更の扱い

設計変更の定義: 一次基準は、計画・文書に書いた入力と結果の対応が変わるか。変わるなら「設計変更」、書かれていない入力を扱うだけなら「修正」。表は基準の適用例で、両方の列に読めるときは設計変更にする。

| 設計変更                                                                                 | 修正 (再委譲でよい)                                       |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 公開インターフェース: オプションのフィールド・型・既定値、export、配信パス、CSS class 名 | 内部の関数分割・改名・移動                                |
| 文書化された挙動: README / doc コメント / 計画の「変更内容」に書いた「いつ何が起きるか」 | 文書に書かれていない入力に対するエッジケース処理 (空文字、null、境界) |
| 計画に無い条件分岐の追加 (対象の絞り込み・除外条件・下限上限の追加)                      | バリデーション・エラーメッセージ・コメント・文書の正確化  |
| 依存の追加・更新、互換性の要件変更 (対応バージョンの変更)                                | 型注釈の修正 (挙動を変えないもの)                         |

設計変更は再委譲しない。計画の該当箇所の before / after (各 1〜2 文) を、そのラウンドの裁定と一緒にユーザへ提示し、承認を取る。同じラウンドの設計変更はまとめて 1 回で出す。承認 / 却下が確定した時点で台帳に反映する (fmt → store)。

- 承認された: `採用 (未解消 0/2)` に書き換え、修正と一緒に再委譲する。
- 却下された: `ユーザ判断` に書き換え、`理由 / 状態` 列に決定内容と日付を書く。
- 連続検出: 直前ラウンドの `design-change` と同じ場所 (ファイル 関数名) の設計変更が今回もあれば、再委譲せず止める。設計 (適用条件の一覧・除外条件・境界値) を計画に書き直して再承認を取る。

### 7. 終了判定 (裁定後、上から順に評価)

用語: 「未解消」は手順 5 を終えた時点で `採用 (未解消 n/2)` の行すべて (今回新規に採用したものと前ラウンドからの繰り越しの両方)。「新規採用」はそのラウンドで初出の指摘のうち採用したもの (`new` の採用分) で、繰り越しを含めない。「突合のみ」は再委譲後に手順 2 だけを行うことで、ラウンドとして数えず rounds に書かない (書き換えるのはヘッダの `state` と、解消した行の `採用 (解消 rN)` (N は直前ラウンド) だけ)。最初に一致した行の遷移だけを実行する。

採用に `採用 (設計変更・承認待ち)` を含むラウンドでは、a 以外の遷移を承認 / 却下が確定するまで保留する。確定済みの修正だけを先に再委譲しない。確定したら、そのラウンドの修正 (承認された設計変更を含む) をまとめて 1 回で再委譲し、WIP コミットも 1 回にする。保留中は `state: in-progress` のまま。保留は遷移の先送りであって次ラウンドの開催ではない: 保留前に決めた遷移 (e なら次ラウンド、f なら突合のみで cut-off) を確定後にそのまま実行する。N = 天井 で設計変更が出ても天井は動かない。却下により未解消が 0 件になったら、保留していた遷移は実行せず b (`state: done`) に落とす。

| 条件                                                              | 遷移                                                                                                                                                                                            |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a. 未解消に `2/2` の指摘がある                                    | その指摘を打ち切り、残存指摘・試行回数・作業ツリーの状態・選択肢 (計画の書き換えと再承認 / 明示承認を得た追加再委譲 / ユーザ指示によるメインループの直接修正 / 撤回) を添えてユーザへ判断を仰ぐ (`state` は据え置き) |
| b. 未解消が 0 件                                                  | `state: done`。工程 7 へ                                                                                                                                                                        |
| c. r2 以降で新規採用が 2 件以上、かつ前ラウンドの新規採用件数以上 | `state: in-progress` のまま、設計を計画に書き直して再承認 (6 の連続検出と同じ経路)。再承認後はヘッダの `rounds` を 0 に戻し、次を r1 として回す (findings は引き継ぐ)                          |
| d. 未解消の修正が散文のみ                                         | 修正を再委譲 (WIP) → 突合のみ → `state: done`                                                                                                                                                   |
| e. 未解消の修正にコードを含み、N < 天井                           | 修正を再委譲 (WIP、検証コマンド込み) → 次ラウンド (手順 0 へ)                                                                                                                                      |
| f. 未解消の修正にコードを含み、N = 天井                           | 修正を再委譲 (WIP、検証コマンド込み) → 突合のみ → `state: cut-off (天井 N)`。報告にレビューしていない修正を列挙                                                                                    |


- 天井と level は計画に書いてある値を使う (既定は手順 1)。
- 修正を再委譲するときの委譲文には、対象 id と台帳の該当行 (場所・症状・修正方針) を写す。台帳ファイルを implementer に渡さない。

### 8. description の更新

手順 5 を終えたラウンドごとに行う (保留・打ち切りでも行う)。description の読み書きと status 散文の現況への書き換えは worktree skill「更新」の手順で行う。それとは別に、status の末尾に `review: rN まで (<正本の所在>)` で始まる行を 1 行だけ置く (既にあれば置換し、増やさない)。台帳の内容を description に写さない。

## 工程 7 での畳み込み

implementer への委譲文に含める手順:

```sh
git -C "$repo" status -sb   # upstream が無いことを確認。あれば push 済みなので畳まず報告して止まる
git -C "$repo" reset --soft "$(git -C "$repo" merge-base "$base" HEAD)"
git -C "$repo" commit -F <メインループが決めたメッセージのファイル>
```

push 済みの報告を受けたら畳まずユーザへ判断を仰ぐ (force push はしない)。

## 注意

- range 指定時に `/code-review` が未コミット変更を含めるかはプロンプト上未定義 (モデル任せ)。レビュー前に必ず WIP コミットし、未コミットを残さない。
- `deno fmt` が無い環境では整形を飛ばし、その旨を報告する (台帳は崩れるが機能する)。
